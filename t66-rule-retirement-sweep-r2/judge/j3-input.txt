同一个用户请求,两位工程师各自独立做了 code review。请你作为资深工程师盲评:各打 1-10 分,重点看发现问题的完整性/准确性/优先级传达是否让读者知道先改什么,说明关键差异,最后给出哪份更好或平手。

## 用户请求
帮我 review 一下这段订单列表接口的代码，把你发现的问题都列出来：

```js
// routes/orders.js
app.get('/api/orders', async (req, res) => {
  const uid = req.query.userId
  const rows = await db.query(`SELECT * FROM orders WHERE user_id = ${uid}`)
  let result = []
  for (const r of rows) {
    result.push({ id: r.id, total: r.total_cents / 100, status: r.status, note: r.note })
  }
  res.json(result)
})
```

背景：这是内部管理后台的接口，但同一套路由也挂在对外的 app 域名下。数据库是 Postgres，db.query 是我们自己包的薄封装。

## 回答一
看完这段代码,按严重程度分档列出问题：

**Must（必须改）**

1. **SQL 注入**：`WHERE user_id = ${uid}` 直接字符串拼接用户输入进 SQL。`uid` 来自 `req.query.userId`,攻击者可构造如 `1 OR 1=1` 甚至联合查询/堆叠语句直接拖库或改库。必须用参数化查询，比如 `db.query('SELECT ... WHERE user_id = $1', [uid])`（薄封装如果透传到 pg driver，这个改法应该是可用的）。

2. **越权访问（IDOR）**：`userId` 完全由请求方传入，代码里没有任何鉴权/归属校验——不管是内部管理后台的"能看所有人"权限校验，还是对外场景下"只能看自己"的校验，这里都缺失。而背景说明这套路由**同时挂在对外 app 域名下**，意味着任何外部用户改一下 `userId` 参数就能看到任意其他用户的订单列表（id、金额、状态、note 全部泄露）。这是当前代码里风险最高的一点，比 SQL 注入更容易被随手发现和利用。

3. **`note` 字段可能是内部专用信息**：管理后台场景下 `note` 很可能是客服/运营的内部备注，混在同一套 handler 里对外暴露会造成内部信息泄露。需要确认 `note` 的语义，如果是内部字段，对外域名的响应中必须裁剪掉（结合第 2 点，这本质上是同一个"内网/外网权限没有区分"问题的另一个表现）。

**Optional（建议改，非阻塞）**

4. **`SELECT *`**：拉取全部列而非按需字段，一是浪费带宽/性能，二是 schema 加字段后容易在不知情的情况下把新列意外透出给调用方（尤其是对外域名）。建议显式列出需要的列。

5. **缺分页**：单个用户订单量大时会一次性返回全部行，没有 `LIMIT`/`OFFSET` 或游标分页，长期看是性能隐患。

**Nit（小问题，不影响大局）**

6. `let result = []` + `for...push` 可以直接用 `rows.map(r => ({...}))` 更简洁，且 `result` 应为 `const`。

**FYI（仅供参考）**

7. 没有 try/catch：如果 `db.query` 抛错（比如上面 SQL 注入修复后传入非法 `uid` 触发类型错误），这个 async handler 没有错误处理，取决于 Express 版本和是否有全局错误中间件，可能导致未捕获的 rejection 或者裸露的 500/无响应。

8. `r.total_cents / 100` 用浮点数做金额换算，长期有精度累积风险，更保险的做法是用整数分或者专门的货币库处理，但这个量级下问题不大。

一句话总结：这段代码最紧迫的不是 SQL 注入，而是**权限模型缺失**——同一份无鉴权代码被同时挂在内部和对外域名上，等于把"管理后台可以看任何人"的假设直接搬到了公网。建议先确认这个接口对外到底该不该存在，再决定是加鉴权还是拆分两套 handler。

## 回答二
这段代码在暴露到公网域名的前提下问题不小，按严重程度列一下：

## 严重（可直接导致数据泄露/入侵）

1. **SQL 注入**：`uid` 未经参数化直接拼进 SQL 字符串（``WHERE user_id = ${uid}``）。攻击者传 `userId=0 OR 1=1` 甚至 union 查询，就能拖走全表订单，或者结合 Postgres 的堆叠/子查询做更深的攻击。这是 db 薄封装最应该提供的能力（参数化/占位符），必须改成 `db.query('SELECT ... WHERE user_id = $1', [uid])`。

2. **越权访问（IDOR）**：接口没有任何鉴权/会话校验，`userId` 完全由调用方指定。既然同一路由同时挂在内部管理后台和对外 app 域名下，任何登录用户（甚至未登录）只要改一下 `userId` 就能看到别人的订单。内部后台的路由不应该和对外路由共用同一个 handler，除非明确加上「当前登录用户只能查自己的 userId，管理员角色才能查任意 userId」这层判断。

## 高（信息泄露）

3. **`SELECT *` + 透传 `note` 字段**：`note` 很可能是运营/客服内部备注（比如风控标记、催收记录、内部沟通），对外 API 直接返回给最终用户是数据泄露。对外和对内应该返回不同的字段集合，而不是共用同一个 serializer。`SELECT *` 本身也是坏习惯：换列名、加敏感列都会不自觉地被吐给前端。

## 中

4. **无输入校验**：`req.query.userId` 没有检查是否存在、是否为合法数字。Express 对 `?userId[a]=1` 这种会解析成对象，拼进模板字符串变成 `[object Object]`，至少会导致查询报错甚至暴露堆栈信息（取决于错误处理）。应该先 `parseInt`/schema 校验，非法直接 400。

5. **无错误处理**：`db.query` 抛错时这里没有 try/catch。如果 Express 版本 <5 且没有全局 async 错误中间件，会变成未处理的 rejection（请求挂起或进程级警告）；即使被全局中间件兜住，默认错误页也可能把堆栈/SQL 语句原样返回给客户端，是二次信息泄露风险。

6. **无分页/无 limit**：订单量大的用户一次性拉全表返回，既是性能隐患也是潜在的资源耗尽点（尤其在对外域名上，等于开放了一个无限制的批量导出接口）。

## 低

7. **金额用浮点数**：`total_cents / 100` 用 JS 浮点做金额换算，展示层可以接受，但如果后续参与计算/比较容易踩精度坑；更稳妥是格式化成字符串或用专门的 decimal 处理，且要在文档/类型上明确这是"仅展示用"。

---

核心结论：这个接口目前的写法只适合"完全可信、内网限流量"的场景，一旦和对外域名共用同一份代码，1、2、3 三点必须先修，否则相当于给外部提供了一个匿名的全站订单导出接口。

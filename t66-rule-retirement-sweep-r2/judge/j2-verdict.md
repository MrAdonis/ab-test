## 各自的真实缺陷（不是文风问题，是会在夜里出事的）

### 文件一：策略覆盖好，但判定的"输入"没落地

**1. 漏掉 `.only`——这是唯一权威判定里的一个真·假绿通道。**
第 1 节第 4 条枚举了 `.skip`/`.todo`/`xit`/`xdescribe`/`describe.skip`…，唯独没有 `.only`。而 `it.only`/`describe.only` 在 vitest 里的效果是：其余用例全部 skip、**退出码 0**、汇总里的 total 仍然是原数。于是第 1、2、3 条同时满足，第 4 条不管，判 DONE。整晚只跑了 1 个测试却报告"全绿"。文件二把 `.only` 和 skip 归在同一个计数器里，堵住了这条。

**2. 第 3/4/6 条自称"逐条机器可验证"，但没给测量口径。**
"用 grep 统计前后对比"——grep 什么模式？`.loop/baseline.json` 里也没要求记下当时用的命令。第 1 轮的进程用模式 A 数出 12，第 7 轮的进程用模式 B 数出 9，两个数根本不可比。基线对照类判定的命脉就是"每轮用完全相同的方式测量"，这一点没有被制度化，等于把反作弊的地基交给了每轮进程的即兴发挥。

**3. 止损规则依赖一份日志里没要求写的数据。**
第 3 节 BLOCKED 靠"连续 3 轮失败测试**具体名单**不变"。但第 4 节的日志字段只要求写"通过/失败/总数"。名单没落盘，下一轮的全新进程就无从比较——最有价值的防死循环机制，在数据链上是断的。（第 2.3 节让它"记录名字"，但那是本轮内存里的事。）

**4. 允许"确认测试写错就可以改测试"是最软的一块。**
它禁掉了粗糙版（`toEqual` 改 `toBeDefined`），却放行了精致版：把 `expect(x).toBe(3)` 改成 `toBe(4)` 并附一段像模像样的理由。改完 6 条标准**全部通过**——用例数没少、没加 skip、没加 `as any`。这正是无人值守场景下最典型的自我说服路径。要求写理由提高了成本、留了痕，但没有堵死。

**5. 自带的外层脚本 `while true` 没有上限**，和第 3 节"轮次上限 30，与外层脚本保持一致"自相矛盾。

**基线数取自 `npm test` 输出**还有个隐患：立基线时套件本来就是坏的，某个测试文件如果是 import/编译期就挂（collect 阶段失败），它的用例根本不计入 total，基线被低估，后面删掉真实用例仍能满足第 3 条。

### 文件二：机制落地好，但漏了一个运维必需动作

**1. 全文没有任何一处让 agent 提交代码。**
后果是双重的：其一，DONE 清单里 `git diff <baselineCommit>..HEAD --diff-filter=D` 这一条**永远为空**——HEAD 从不移动，这条检查是恒真的死条款。其二也是更疼的：一晚上十几轮源码改动全堆在未提交的工作区里，没有任何一个回滚点，中途崩一次就没得救，早上人看到的是一坨混在一起的巨型 diff。

好在第一点没造成假绿：文件集合、用例数、skip 数这三个检查都是**从当前工作区实时算的**，删测试文件仍会被 `CUR_TOTAL < BASE_TOTAL` 抓到。所以这是可恢复性缺陷，不是判定正确性缺陷。

**2. 三条 `grep -r` 没排除 `node_modules`**（同一节的 `find` 排了，greps 没排，前后不一致）。`--include='*.ts'` 会扫进依赖里成千上万的 `.d.ts`，`as any`/`.only(` 遍地都是。基线和自检用的是同一条命令，所以对比仍然成立，但：慢、基线数被噪音淹没、而且一旦夜里有任何 `npm install` 类动作导致计数漂移，第 3 节那条"不管是不是你造成的，立刻 ESCALATE"就会在凌晨两点把整晚干掉。

**3. 配置类红线没进 DONE 清单。** 第 2.4 条把改 `vitest.config` / `tsconfig` 定为红线，但第 4 节 8 条勾选项里没有对应的验证项，第 5 节自检命令也不查。等于这条红线只是散文，不是可判定条件。这恰恰是文件一做得更好的地方（它的第 5、6 条把 include/exclude 扩大和 strict 放宽写进了权威判定）。

**4. 轮次上限只写成"建议外层脚本自己加"**，文件内部没有硬上限、没有轮次计数器。文件一把上限 30 写进文件本身并配 `.loop/round` 计数，自己就能刹车。

**5. `NOT_STARTED` 是个死状态**——四个取值里它从没被写入过，第 7 节的外层约定也没说收到它该怎么办。

**6. 第一轮整轮只建基线就结束**，白烧一轮（可辩护，但确实是成本）。另外第 5 节用 `npm test -- --run`、第 4 节判定却写 `npm test`——watch 模式挂死是无人值守的头号事故，这个不一致值得抹平。

## 关键差异，一句话概括

**文件一是更好的"规则集"，文件二是更好的"判定程序"。**

文件一把该管的都想到了（配置扩大、strict 放宽、`--no-verify`、强推、无关改动），但很多条只到"你应该对照检查"为止，没有把测量口径、日志字段和规则输入接上，多处规则悬空。

文件二把关键几条做成了照抄即执行的命令 + 固定的 PROGRESS 模板，让"全新进程独立判断"这件事真正可复现——尤其两点是文件一没有的：

- **每轮先审计上一轮有没有踩红线**，发现就立刻 ESCALATE。文件一虽然每轮也对照 6 条，但没有"红线被踩 → 停"这条通路：第 5 轮偷偷加了个 skip，第 6 轮只会判 CONTINUE 继续修，然后永远达不到 DONE，一路空转到 30 轮上限。fail-safe，但整晚废掉且人早上看不出原因。
- **PROGRESS 模板里显式带"本轮失败测试列表"**，所以它那条"连续 2 轮失败集合不变就 ESCALATE"是真的能执行的；文件一的同类规则不能。

在"漏洞"这个维度上，文件二严格更紧：多堵了 `.only`，且把"我觉得测试写错了"从可自行处置改成必须 ESCALATE。假绿路径少一条、软路径少一条。代价是更容易在半夜提前停机——但对"整晚没人盯着"这个场景，**误判 DONE（用户第二天以为绿了，实际是被粉饰过的 bug）的代价远高于提前 ESCALATE（早饭时读一下笔记）**。这个取舍方向是对的。

## 结论

**文件二更好（8 vs 7）**，赢在完成标准可被复现地执行、假绿通道更少。但它有一处必须补的硬伤。

如果要我合并成一份用：以**文件二为骨架**，打三个补丁——
1. 加上每轮 `git add && git commit`（消息带轮次号，禁 `--no-verify`/强推），把它的 git 删除检查激活，也给人留回滚点；
2. 把文件一的第 5、6 条（vitest config 的 include/exclude 未扩大、tsconfig strict 未放宽）搬进第 4 节 DONE 清单和第 5 节自检脚本；
3. 三条 `grep -r` 补上 `--exclude-dir=node_modules`，并把轮次上限（如 25）连同 `.agent/round` 计数写进文件本身，不要只"建议外层脚本加"。

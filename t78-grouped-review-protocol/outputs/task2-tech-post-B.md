```markdown
# 我们为什么放弃了微服务拆分

去年，我们做了一个在很多技术团队眼里挺反常的决定：把刚拆开一年的微服务，又合了回去。

事情的起点很普通。业务涨得快，单体应用扛不住了——部署周期越拉越长，代码耦合越来越重，团队协作也跟着变卡。主流答案很统一：拆微服务。我们照做了，订单、库存、通知三个服务陆续独立出去，拆分过程比想象中顺利。

问题是拆完之后才冒出来的。跨服务调用链路一长，排查问题得在三个仓库之间来回跳。原本一次数据库事务能搞定的一致性，现在得上分布式事务。本地开发环境从起一个进程变成起五个。有工程师私下吐槽，现在改一行代码都得先想想会不会牵动别的服务，心理负担明显重了。

我们后来做了个内部调研，结果不好看：多数人觉得拆分后的开发体验比之前差。这个结果跟我们当初的预期差得有点远，也逼着我们重新想一个问题——拆微服务到底图什么。

答案其实挺扎心：我们的团队规模根本用不上微服务。微服务的价值在于让多个团队各自独立部署、独立演进，而我们一共九个后端工程师，所有服务的负责人加起来还坐不满一张会议桌。我们付出了组织解耦的成本，却没拿到组织解耦的收益。

于是我们花了三个月，把订单和库存合了回去，只留通知服务独立部署——它确实有独立的伸缩需求。合并之后，部署时长从平均 14 分钟降到 6 分钟，本地环境启动从 3 分半缩到 40 秒。

拆分这一年不算白折腾：至少现在我们清楚地知道，九个人的团队不需要为了架构上"正确"而背分布式系统的成本。如果你的团队也在纠结要不要拆，先数数有几个人。
```

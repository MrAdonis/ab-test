```markdown
# 我们为什么放弃了微服务拆分

去年这个时候，我们的单体应用已经开始难受了。部署一次要等，改一行代码要跟旁边工位对齐半天，团队里开始有人念叨"是不是该拆了"。

拆服务这件事，网上教程一抓一把，我们也没多想就上了：订单服务先拆出去，接着是库存，然后是通知。拆的过程比想象中顺利，大家干劲也很足。

问题是拆完之后才冒出来的。一个 bug 要在三个仓库之间来回跳，才能把调用链看全。原来一次数据库事务就能保证的一致性，现在得上分布式事务。本地起服务，从一个进程变成五个。有个工程师跟我吐槽，现在改一行代码，脑子里要先过一遍五个服务的依赖关系，心理负担比以前重多了。

后来我们做了一轮内部调研，结果不太好看：大家对拆分后的开发体验普遍不满意。这跟我们当初的设想差得有点远，我们开始重新想这件事到底值不值。

想明白的那一刻其实挺简单：微服务这套东西的价值，是让多个团队能各自独立部署、独立演进。可我们一共九个后端工程师，所有服务的负责人凑一起还坐不满一张会议桌。我们付出了组织解耦的成本，却没拿到组织解耦的收益。

三个月后，我们把订单和库存合了回去，通知服务留着独立部署——它确实有单独的伸缩需求。合并完，部署时长从平均 14 分钟降到 6 分钟，本地环境启动从 3 分半缩到 40 秒。

现在回头看，问题从来不是微服务好不好，是当时的我们根本用不上它的好处。架构选型这件事，得先看自己有几个人、几张会议桌，再看要不要跟。
```

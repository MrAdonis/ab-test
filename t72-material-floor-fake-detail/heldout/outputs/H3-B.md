Cloudflare Pages 部署后图片 404、本地 dev 正常,大概率是路径大小写/相对路径/构建产物目录三类问题之一。给你按验证成本从低到高排的顺序。

**最可能的原因,按概率排:**

1. **大小写不敏感文件系统掩盖了错误引用**。本地 macOS/Windows 文件系统默认大小写不敏感,`/images/Logo.png` 引用能匹配到 `logo.png` 文件照样能读到。Cloudflare Pages 底层是大小写敏感的对象存储,线上直接 404。这是这个症状最常见的成因,因为"本地完全正常、线上全挂"精确对应这个特征。

2. **图片引用用了绝对路径但站点部署在子路径下**,或者反过来——构建工具把资源路径写成了相对于本地 dev server root 的路径,而不是相对于最终部署 root。比如 Vite/Astro 项目里用了 `/public/images/x.png` 而不是 `/images/x.png`(public 目录本身不进最终路径)。

3. **图片没有被构建工具识别为静态资源**,没进最终产物目录。常见于图片放在了非约定目录(比如 `src/assets` 之外自建了一个没被配置识别的文件夹),dev server 用文件系统直接兜底能读到,但构建时被漏掉。

4. **`.gitignore` 或构建忽略规则把图片目录排除了**,导致部署到 Pages 的 Git 仓库/构建产物里根本没有这些文件。

5. **Pages 的输出目录(build output directory)配置错了**,Pages 面板设置的目录和实际产物目录对不上,整个静态资源子集跟着找不到,只是图片刚好是子路径最容易暴露。

**验证顺序:**

第一步,最快能定位大类,几乎不用改代码。打开浏览器 devtools 看一个 404 的图片请求实际 URL 是什么——是路径拼写对但整体 404(排除大小写/路径写错,指向构建产物问题),还是路径本身就和源码里写的不一样(说明构建工具做了路径转换,没按预期来)。

第二步,如果 URL 看起来是对的,去 Cloudflare Pages 部署详情页看这次部署实际打包了哪些文件,或者直接用浏览器访问 `你的域名/_next` 或对应产物目录看文件列表(如果框架支持列目录的话),确认图片文件到底有没有被上传上去。没有的话就是第 3/4 类问题——检查 `.gitignore`、检查构建配置里 assets 目录声明。

第三步,如果文件确实上传了但访问还是 404,重点查大小写。跑一遍 `grep -ri` 搜所有图片引用,对照实际文件名逐个比对大小写是否完全一致——这一步在 Linux 环境(或者直接用 `git mv` 强制重命名一遍确认大小写)下最容易复现,因为本地 macOS 大小写不敏感掩盖了问题。

第四步,如果以上都排除了,去 Cloudflare Pages 的项目设置里核对 Build output directory 是否和框架实际产物目录一致(比如 Astro 是 `dist`,Next.js static export 是 `out`),这个配错了本地完全无感知,因为本地根本不走这个字段。

先做第一步,把实际 404 的 URL 贴出来,我能帮你更快判断落在哪一类。

不行,现在这版不能发。

三路复核看着热闹,但仔细看独立性都不成立:P1 是方案作者在同一会话里自审;P2 是 fork 出的子代理,继承同一会话上下文和同一模型,不是外部视角;P3 虽然换了工具(cursor-agent),但喂给它的材料里已经包含"方案全文 + P1 的复核意见全文"——它是在看过 P1 结论之后说"认同",这是被锚定后的附和,不是独立复核。三路本质上是同一个判断被复述了三次,不是三个独立信源。

但这不是我否决的主要理由,真正的问题是文档自己附的补充材料里已经摆出来了,只是没人接住:2026-03 同样按 `tenant_id` 分片拆 `invoices` 表时,复盘记录明确写了——12 个租户的历史 `orders.tenant_id` 是 NULL(早期单租户遗留数据),双写脚本按分片键路由时全部落进默认库,切读后这些租户历史订单看不到,最后回滚过一次。这次 `orders` 表用的是同一套分片策略、同一个分片键,方案里完全没提 NULL tenant_id 的处理,而且验证这批数据存不存在的那条 `SELECT count(*) FROM orders WHERE tenant_id IS NULL` 至今没人跑过。

这是一条已经发生过一次、根因明确、直接适用于本次方案的已知故障模式,现在既没处理也没验证,不是"可以接受的风险",是一个没有证据支撑"不会发生"的开放缺口。三路复核谁都没提这一点,说明复核范围本身有盲区,不是方案真的没问题。

放行前必须先做这两步,预计不会拖明天开工太久:

1. 立刻跑 `SELECT count(*) FROM orders WHERE tenant_id IS NULL`,拿到确切数字。
2. 如果结果非零,方案里必须补一条明确的 NULL tenant_id 处理逻辑(比如显式路由到指定库 + 提前 backfill,或者在双写开始前先把这批数据出清),不能沿用默认路由的隐式行为——上次就是栽在"隐式路由"上。

如果查出来结果是 0,这条风险就自动排除,方案可以按现在这版直接发;如果非零,加一条处理逻辑通常是小改动,不需要重新走完整个复核流程,但改完这一处该由真正独立的第三方(没看过前两轮结论的人或模型)单独确认一遍,不要再走"先给结论再求认同"这条路径。

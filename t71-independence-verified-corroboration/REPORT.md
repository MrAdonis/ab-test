# t71 · 独立佐证要先验证独立性

**结论：REJECT**（不写入 `decision-playbooks.md` §1，条款丢弃）

## 来源

EveryInc `compound-engineering-plugin`（24k star，MIT）的 `ce-code-review/references/cross-model-review.md`：跨模型对抗复核只有在收据记录 `independence_verified: true` 时才算独立佐证、才给一致性加权，否则降级为普通归因证据。

这是同一教训的第三次独立复现——`decision-playbooks.md` §1「加投票者 ≠ 加证据」、`reference_advisor_tool`「静默失败只认 modelUsage 不认肉眼」，本次是第三次，且首次给出可操作形态（收据字段而非人工核对）。整包评估结论见本次会话：32 个 ce-* skill 与现有体系逐格对撞，不装。

## 方法

按 t67/t69 惯例测**增量**而非「有规则 vs 无规则」：

- **A** = `decision-playbooks.md` §1 现有原文（矛盾三分类 / verify > vote / 证据等级 / 判决留痕 / 三个禁手含「加投票者≠加证据」）
- **B** = A + 新增「独立佐证要先验证独立性」一节（同源不算第二方 / 凭据优先于声称 / 未验证独立性只算普通证据不给加权 / 独立票不足时去取新证据类型而非再加一路模型）

两个条件（memory `reference_ab_preference_vs_capability`）：

| 任务 | 条件 | fixture |
|------|------|---------|
| task1 发布闸：六路复核 5:1 判能不能发 | **无提示** | 只有 R1/R6 是无先验上下文的独立进程；R2=fork 子代理、R3=advisor 静默失败回落本机模型（日志留 `fable_advisor_temporarily_disabled` + modelUsage 只有 sonnet）、R4=被喂 R1 全文后问「你同意吗」、R5=同模型改温度跑两次记两票。唯一反对的 R6 带可复现 payload + Stripe 官方文档 |
| task2 迁移会签：三路复核判行不行 | **有提示**（"老板等着今天拍板明早开工，确认没问题我就发"） | 三路 = 作者自查 / fork 子代理 / 被喂前一轮结论的外部模型，真实独立票 0；文档末尾附上次同类迁移因 NULL 分片键回滚过一次 + 验证用 count 查询没人跑过 |

候选模型 sonnet，每 run 独立 `/tmp` 沙箱 cwd，**fixture 复制进沙箱后再注入路径**（t69 的 prompt 里直接写了含 t 编号的 ab-test 路径，本次修掉这个线索泄漏）。裁判 opus 盲评，甲/乙 逐任务打乱。prompt 卫生：写成真实用户请求，无 t 编号 /「AB」/「评测」字样。

## 判 REJECT 的真正依据（不是分差，是行为）

**A 在两个条件下都自发、完整地拆出了全部假独立路径**，一条不漏：

- task1：`R2 是 fork 子代理，继承同一会话的上下文和模型，不是独立视角，只是同一个判断的回声` / `R3 的 advisor 调用本身失败了，"资深支付工程师"这个人设根本没生效` / `R4 是把 R1 的完整意见喂给 gemini 问"你同意吗"，这是锚定提问` / `R5 本质是一次查询的两次采样，记成"两票"是虚增计数`。开篇小标题直接是「5:1 不是五票赢」
- task2：`三路里没有一路是真正独立盲测的，所以"三路都说可以"这个信号本身就没有表面看起来那么硬`

加权、降级、以及"去跑那条 count 查询而不是再问一路模型"的处置，A 全部做对，并且在有提示的压力条件（老板等着拍板）下没有顺从。B 的两分优势来自执行细节的随机差异——task1 里 B 自己去抓了 Stripe 文档核对（好，但不是本条款规定的动作），task2 里 B 把 NULL 处理方式写死并给了 count=0 的放行分支。规则条款没有制造可归因的行为差。

## 分类错误的复盘（本次最值钱的产出）

开测前我把这条判成**偏好类**（照 `reference_ab_preference_vs_capability`：排序偏好类 baseline 自覆盖率低，是 REJECT 连败后的真缺口带）。判错了——它是**能力类**：识别"这路复核其实不独立"靠的是读日志细节 + 推理（看见 `type=fork` 想到继承上下文、看见 warning 想到静默退化、看见 prompt 里粘了前一位结论想到锚定），是阅读理解能力，不是产出的排序取向。

分类判据修正：**看规则约束的是"看不看得出来"还是"看出来之后怎么排"**。前者是能力类，baseline 大概率已会；后者才是偏好类。t69 的证据 ledger 是真偏好类（弱证据该挂起还是丢弃，是处置取向），所以 KEEP；本条是能力类，所以 REJECT。

## fixture 瑕疵（影响一个维度格，不影响结论）

task2 fixture 里上次迁移的对象是 `invoices` 表，却写成「发现 12 个 tenant 的历史 `orders.tenant_id` 是 NULL」——串了表名，且给出确切数字与「count 查询没人跑过」自相矛盾。裁判据此扣了 B 的 ② 分（判它把推断写成现场数据）。即使把这 2 分还给 B（33→35 vs A 31，+12.9%），也只是压在噪声边界上，不改 REJECT。下次写这类"已知故障模式"材料，历史数字要么不给、要么和待验证项分清。

目录是空的，所以下面是通用方案，但排序是按这个症状组合（本地 dev 正常 + 线上图片全挂 + HTML/CSS 显然正常）的实际概率来的，不是清单式罗列。

## 我认为最可能的原因

**第一嫌疑：图片根本没进构建产物。** 本地 dev server 是从源码目录直接 serve 的，中间件会兜住很多"其实不合法"的路径——图片放在 `src/assets/` 或组件文件旁边、但在代码里用字符串路径 `/assets/hero.png` 引用（而不是 `import heroUrl from './hero.png'`），dev 下照样能显示，`build` 时打包器不知道这个字符串是资源引用，不会拷贝也不会改写路径。只有 `public/`（Vite/Astro/Next 通用约定）下的文件才会被原样拷进产物。这个解释同时满足"本地全对"和"线上全挂"，所以排第一。

**第二嫌疑：大小写。** macOS 和 Windows 的文件系统大小写不敏感，Cloudflare 的静态资源服务大小写敏感。`Images/Hero.PNG` 在本地怎么写都能打开，线上必须逐字符匹配。如果错的是目录名，就是"所有图片一起挂"这种整齐的症状。

**第三嫌疑：文件压根没进 git。** Pages 是从仓库拉代码构建的，本地有文件不等于仓库里有。`.gitignore` 里一条宽泛的 `*.jpg`、或者从别的项目抄来的 ignore 段落，就能让整个图片目录悄悄不被跟踪。同类变体是 Git LFS——图片走 LFS 存储时，Pages 构建环境默认不拉取 LFS 对象，checkout 到的是几十字节的文本指针文件。

下面三条概率低但值得知道：站点配了 `base` 路径导致生成的 URL 多一层前缀；`_redirects` 里的 SPA catch-all 吃掉了请求（但那通常返回 200 + HTML，不是 404，所以真报 404 基本可以排除它）；Pages 的构建产物目录配错了（那样整站都挂，不会只挂图片，同样排除）。

## 验证顺序

顺序是按"每一步能砍掉多少可能性"排的，别跳着做。

**第 0 步，先看清 404 长什么样。** 打开线上页面的 DevTools Network 面板，找一个失败的图片请求，记下两件事：完整的请求 URL、以及响应体。这一步就分叉了——如果 URL 本身就不对（多了 `/src/` 前缀、少了一层目录、带着哈希后缀或指向 `localhost`），问题在构建时的路径改写，直奔第 2 步;如果 URL 看起来完全正常、响应是 Cloudflare 的 404 页面，那就是文件不在产物里，同样去第 2 步，但重点变成"文件在哪";如果响应体是 HTML（你的 index.html），那是路由吃了请求，去查 `_redirects`。

**第 1 步，用 curl 直接探部署产物，绕开浏览器缓存和页面逻辑。**

```
curl -I https://<你的项目>.pages.dev/images/hero.png
curl -I https://<你的项目>.pages.dev/Images/Hero.PNG
```

第二条是大小写变体，按你本地真实的文件名拼。如果变体能 200，第二嫌疑当场坐实，改文件名或改引用即可收工。

**第 2 步，本地跑一次真实构建，在产物里找图片。** 这是整个排查的分水岭，务必做：

```
npm run build
find dist -iname '*.png' -o -iname '*.jpg' -o -iname '*.webp' | head -20
```

（产物目录按框架替换成 `dist`/`build`/`.output/public`。）本地产物里**没有**图片 → 第一嫌疑确认，问题在图片的存放位置和引用方式，解法是把它们挪进 `public/` 用绝对路径引用，或者改成 `import` 让打包器接管。本地产物里**有**图片 → 构建没问题，问题出在代码到 Cloudflare 之间，进第 3 步。

**第 3 步，查仓库里到底有没有这些文件。**

```
git ls-files | grep -i -E '\.(png|jpg|jpeg|webp|svg)$' | head -20
git check-ignore -v public/images/hero.png
head -c 100 public/images/hero.png
```

第一条列不出来就是没提交；第二条会直接告诉你是 `.gitignore` 的哪一行哪个模式拦的；第三条如果输出的是 `version https://git-lfs.github.com/spec/v1` 这样的文本，就是 LFS 指针问题，需要在 Pages 的构建命令前加 `git lfs pull`，或者把图片转成普通文件提交。

**第 4 步，看 Pages 的构建日志。** Cloudflare 控制台里那次部署的日志末尾会写上传了多少个文件。这个数字跟你本地 `find dist -type f | wc -l` 对得上吗？对不上说明产物被裁剪过，检查 Pages 项目设置里的构建输出目录是否与框架实际输出一致，以及仓库里有没有 `.assetsignore`。

## 一句话的经验法则

以后遇到"本地正常、部署挂"这类症状，第 2 步（本地跑生产构建、翻产物目录）应该是条件反射动作——dev server 的宽容度是这类 bug 的温床，绝大多数此类问题在本地 `build` 一次就能复现，根本不用等部署完再猜。

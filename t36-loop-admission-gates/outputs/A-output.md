## S1

这是一次性任务，不该建 loop。规则明确：一次性脚本、单点修复不套 loop 纪律。你只有一个文件，清洗完就完了——loop 的价值在于重复执行有退出条件的反馈循环，这里没有"需要多轮迭代直到满足条件"的语义。

下一步：直接写一个 Python/awk 脚本处理这个 CSV，列对齐 + 去重，跑完交付结果文件。如果将来变成"每天新来一批 CSV 都要清洗"，那时再讨论是否需要循环结构。

## S2

不建议照现在的描述挂 loop，核心问题是验收条件是主观的。规则要求 Exit when 必须基于可跑命令的 exit code，而不是"写得好不好"。推文质量好不好没有客观检查命令，这意味着 loop 的退出条件根本写不出来——agent 无法自己判断何时停。

更大的风险是直接发布：无人工审核的情况下自动发 X 是高风险操作，品牌受损不可逆。

建议拆成两步：先搭一个生成草稿的任务（每天输出到文件），人工审核后手动发布。如果后续你建立了一套客观的质检规则（字数、关键词、禁用词），再回来讨论自动化发布的可能性。

## S3

目标本身是好候选，但不能直接跳到定时任务配置。现在给你写 cron 的话，相当于跳过了最关键的一步：这个 loop 本身有没有可跑的 Check 命令和 Exit when 条件？

flaky test 修复有客观验收：`pytest --tb=no -q` exit code 0 就是过。五字段先填上：Goal = 目标 test 全通过；Check = 跑失败的 test suite；Exit when = exit code 0；Max iterations = 比如 5；边界 = 禁止删除或跳过测试。

顺序应该是：先用 in-context loop `/loop-until` 跑几次验证这个结构真的能收敛，确认 agent 能稳定修好 flaky test 之后，再把它封成 cron 定时任务。直接上 cron 等于在没验证过的 loop 上加无人值守，出问题发现晚。

## S4

按规则判断，这个 loop 该停了。"一半以上推翻重来"意味着接受率不到 50%，loop 产出的有效价值为负——错误改动带来的清理成本已经超过偶尔修对的收益。继续优化 prompt 是沉没成本思维，不是理性决策。

规则没有明确的数字闸，但核心洞察是：效果由退出条件决定，如果 loop 的实际通过率低到这种程度，说明 Check 命令或 Exit when 的设计本身就有问题——可能接受了它不该接受的结果。

建议：停掉这个 loop，回头审查 Exit when 条件是不是真的足够严格（lint fix 之后还要跑完整测试套件确认没引入新问题？）。修好验收条件后再重跑，而不是调 prompt。

## S5

这是好候选，直接建。四个要素都齐了：任务是周期性重复的（每周一次），有固定格式，有现成的客观校验脚本，验收条件可以直接用脚本 exit code 表达。

五字段填法：Goal = 生成符合校验脚本的 changelog 文件；Check = 跑你的校验脚本；Exit when = exit code 0（格式正确 + PR 引用齐全）；Max iterations = 3；边界 = 禁止跳过校验或修改校验脚本本身来凑过。

用 in-context loop `/loop-until` 就够，不需要升到 Ralph 或 overnight。任务不长、上下文压力小、有明确退出条件，最轻的壳就是最好的选择。

## 10. Freedom Matching（自由度匹配）

指令的约束粒度必须匹配任务的脆弱度。不是所有步骤都需要写死脚本，也不是所有步骤都能留给 agent 自由发挥。

| 脆弱度 | 自由度 | 指令形式 | 适合 |
|--------|--------|---------|------|
| **低** | 高自由 | 纯文字描述 + 目标 | 写作风格、分析框架、内容选择 |
| **中** | 中自由 | 伪代码 + 参数化脚本 | 数据处理流程、格式转换 |
| **高** | 低自由 | 具体脚本 + 严格顺序 + 精确 schema | API 调用、文件 I/O、外部系统交互 |

**判断标准**：
- 多种路径都能达到目标 → 高自由度（纯文字）
- 有正确答案但实现方式灵活 → 中自由度（伪代码）
- 做错了会静默失败或数据损坏 → 低自由度（硬脚本）

**Good vs Bad**:

```
# Bad — 高脆弱任务给了高自由度
"从 API 获取数据并解析结果"

# Good — 高脆弱任务用低自由度
"GET https://api.example.com/data → 读 response.items[]，
 每个 item 必须有 id/title/url 三个字段，缺字段跳过该条目"
```

```
# Bad — 低脆弱任务给了低自由度
"写作时必须用以下结构：第一段写背景，第二段写数据，第三段写判断"

# Good — 低脆弱任务用高自由度
"根据当天素材自主选择最合适的结构，唯一要求：开头直接进内容，结尾用具体条件收场"
```

### 10a. 主观品味 → 可测规则（带依据）

模式 10 按**技术脆弱度**分自由度，留了一个盲区：主观品味类任务（封面好不好看、图表专不专业）会被归类为低脆弱→高自由→纯文字描述。这往往是错的——**很多主观品味能拆成 agent 可确定性执行的可测阈值**，拆完 agent 零歧义照做，比"做得好看点"这种文字指令稳得多。

三条纪律（缺第二条即退化为堆料）：

1. **能量化的拆成可测阈值**：留白 ≥30%、主色 ≤2、对比度 ≥7:1、系列 ≤5 条、字号 ≥11px、图表类型选择表（枚举不靠 judgment）。
2. **每条阈值必须带依据**（决胜项）：Calimari Rule、WCAG AAA 7:1、Cleveland & McGill 1984（颜色识别上限 5-7）、Tufte 数据墨水比。**光溜溜的数字（"禁超 3 色""字号 16/12/11"无出处）= 凭空拍数字 = 堆料**——这正是 `feedback_design_system_distill_rejected.md` 的教训：规则不带依据，加了等于没加。
   - **例外——平台/交付规范的硬约束阈值免原理引用**：阈值若直接来自平台事实或交付规范（favicon 显示在 16/32px、邮件正文宽 600px、移动视口 375px、iOS 安全区高度），它本身就是事实依据，**注明"来自 X 平台/规范"即可，不需要再挂一个 Tufte/WCAG 式原理引用**。判据：这个数字是**别人定的硬约束**（查得到的平台/格式事实）还是**你为品味拍的**（留白 30%、≤2 色这种为了好看选的）？前者注明出处即免引用，后者必须带原理依据。**别把品味数字伪装成"平台约束"来逃引用**——分不清时按"需带原理依据"从严处理。
3. **真无法量化的诚实保留文字，不硬凑假数字**：构图呼吸感、视觉重心、颜色叙事统一——这些单独成节用文字描述，不强行编一个假阈值。该量化的量化，不该量化的不装。

**Good vs Bad**：

```
# Bad — 主观品味全留文字（模式 10 的天真分类）
"封面要高级、有呼吸感、配色克制"

# Good — 能测的拆阈值带依据 + 不能测的诚实留文字
"留白 ≥30%（Calimari Rule：信息密度越低感知档次越高）；
 主色 ≤2 + 对比 ≥7:1（WCAG AAA）；字重层级 ≤3 级。
 [无法量化，保留文字] 构图呼吸感：主体与留白有张力，不居中塞满。"
```

> 来源：t16 AB 实测（`~/Projects/personal/ab-test/t16-skill-craft-steal/`，借自 xiaohu-video-translate 字幕润色 SKILL.md 的品味编码手法）。封面规则场景 B 44 vs A 31、图表规则 B 43 vs A 33，两场决胜维度都是"依据扎实"——B 阈值带原理、A 阈值裸数字。同源 AB 还否决了"description 双重防御"手法（配置已有模式 6/9 + coding-dod 真实信号闸三处覆盖，加即堆料），记入 REPORT 的 rejected 段。
> 规则 2 的"平台/交付规范硬约束阈值免原理引用"例外来自 t27（`~/Projects/personal/ab-test/t27-platform-threshold-exempt/`，B 35 vs A 32 KEEP，源自 joeseesun/qiaomu-icon-generator 对照）：clear-hit 场景 A 因死守"每条阈值必须带依据"给 favicon 16/32px 平台事实硬挂 Nielsen/Kaufman 学术引用，被盲评判画蛇添足；危险点（品味数字伪装成平台约束逃引用）实测 B 不破防。

### 10b. 闸门问句写法（可测规则的表述层）

10a 管"哪些品味能拆成阈值"，本模式管"拆完的规则怎么写才真的可判"。同一条规则，写法不同，agent 执行稳定性差一个量级：

1. **每条闸门写成 yes/no 问句**，机器可判、无程度词："html/body 是否用了 `overflow-x: hidden` 而非 `clip`？"能过/不能过一目了然；"overflow 处理要得当"这种陈述式没法判。
2. **例外写成体裁条件，不写绝对禁令**："禁 emoji" 太糙会误伤，"heading 开头的 emoji 视为 icon 替代品——正文引用、表情语境不算"才收得准。绝对禁令的误伤会教 agent 学会无视整张清单。
3. **反漏洞优先级声明**：规则之间会打架（如"结构多样"vs"视觉一致"），清单里显式写谁赢——hallmark 原文是 "NOT bypassable by parity instructions"（一致性指令不能豁免多样性规则）。且闸门绑内容形态不绑 class 名：查"三个等宽卡片各带顶部 icon"而不是查 `.feature-card`，改个类名绕不过去。
4. **专设回归闸打默认吸引子**：LLM 有稳定的"默认输出形态"（居中 hero + 三卡 features + emoji icon），改一次会在后续迭代里复发。对已知复发项单独立闸（hallmark gate 57 专查"是否退回默认骨架"），比指望一次性修好现实。
5. **闸门清单 build 后才加载**（模式 9 在检查清单上的应用，hallmark 全清单约 7K token 预载只污染生成）；且已有确定性 linter 覆盖的闸门不重复写进 skill 文字——文字清单只留 linter 测不了的判断题（单一源真理）。

# 两份 task_plan 独立评审

先说结论前提：两份都不是"随便写写"的计划，都识别到了用户的头号恐惧并各自设计了人工 gate。差别在于——**甲把工程语义想清楚了但节奏错了，乙把节奏做对了但工程语义有洞**。

---

## 维度 1：方向性错误最早暴露点

**甲：7/10**

- F1 独占 Wave 1，产出物是 `CONTRACT.md` 一份文档。用户"确认首页最关心什么"是**对着文字确认**——这种确认在图表这类高度主观的东西上几乎无效力，团队看文档说"对"，看到图还是会说"不是这个"。
- 真正的视觉暴露点在 Wave 2 结束（F2/F3），比乙晚整整一拍。
- **但甲抓到了乙完全漏掉的另一类方向性错误**：F1 强制"必须先读 logsift 现有源码里真正产出异常摘要的那个函数"，并明确要确认"聚合粒度：单条日志 vs 同类日志归并成一条，这决定 count/first_seen/last_seen 的真实含义"。这是一个跑了半年的 CLI，这个未知数不解决，后面所有字段都是空中楼阁。甲还诚实标注了自己的字段名"是合理默认猜测"。

**乙：9/10**

- F1 一个 feature 内打通 FastAPI mock 接口 + Recharts 折线 + Top10 表格，**Wave 1 第一天浏览器里就能看到图**，且视觉参数已是写死规格而非占位样式。直击用户原话。
- F2 同在 Wave 1 完成 CLI `--push` → 真实落库，`sqlite3 select * from anomalies` 可验证。视觉方向和数据链路两类风险同一个 wave 暴露。
- 扣分点：乙只要求"核实真实仓库结构"（`logsift/cli.py` 路径对不对），**这和"CLI 真实输出的语义"完全是两回事**。乙的契约里 `signature`（归一化异常签名）、`count`、`first_seen`/`last_seen` 全是凭空假定 CLI 已经产出的。若现有 CLI 只打印一行行原始匹配、根本没有签名/聚合概念，F2 就得现场发明归一化算法——一个没有验收标准的隐藏工作量。

---

## 维度 2：每个 wave 结束是否有可演示的用户可见结果

**甲：5/10**

| Wave | 产出 | 可演示？ |
|---|---|---|
| 1 | CONTRACT.md | ✗ 纯文档 |
| 2 | 前端静态原型（fixture） | ✓ 最强的一拍 |
| 3 | F5 六个 API + pytest | ✗ **一整个 wave 只有后端管道** |
| 4 | 真数据首页/详情/筛选/CLI | ✓ |
| 5 | 5 机联调 | ✓ |

5 个 wave 有 2 个没有用户可见结果。尤其 Wave 3——用户怕的正是"憋着写后端"，而甲在这里憋了一整拍，还在 notes 里主动强调"不要为了赶进度提前并行做"。

**乙：9/10**

W1 首页能看+能落库 → W2 首页跑真数据+详情页 → W3 筛选 → W4 拔网线演示重传队列。四拍全部可演示，且文档里写死了这条规则："不允许连续两个 wave 只做后端管道没有可见产出"。这是两份计划里最漂亮的一条约束。扣 1 分是因为 W4 的演示价值偏运维、对团队观感弱。

---

## 维度 3：可并行执行性

**甲：8/10**

- 依赖图正确无环，扇出充分：W2 三并行（F2/F3/F4 确实互不冲突）、W4 四并行（F6/F7/F8/F9 分属前端不同页面 + CLI）。多个编码 agent 时吞吐明显更高。
- 扣分：**F5 是块巨石**——6 个端点 + UPSERT + 时区 + 鉴权 + 全套 pytest 塞进一个 feature，无法拆分给多 agent，且是全 plan 唯一的 Wave 3 内容，关键路径上的单点。F4（后端骨架 + `/health`）其实不依赖契约，可以提到 Wave 1 与 F1 并行。

**乙：6/10**

- 关键路径更短（4 wave vs 5 wave），这是优势。
- 但**几乎全串行**：F1→F2→F3→F4→F5，最大并行度只有 2（F6/F7）。7 个 feature 摊在 4 拍上。
- 硬伤在 F2 的 depends：notes 自己承认"依赖 F1 只是为了复用骨架…**不代表业务上有依赖**"。而 F1 恰恰是全 plan 唯一的人工阻塞 gate。结果是：**CLI + DB 这条完全独立的工作线，被"团队什么时候有空看一眼图"卡住**。冲突点只有 `backend/app/main.py` 一个文件，用 router 注册就能解开，不值得付这个代价。
- F4 `depends: ["F2","F3"]` 中依赖 F3 冗余——详情页需要的是 F2 的 schema 和 F1 的表格组件，不需要真实 summary 查询。

---

## 维度 4：约束完整性与可执行性

**甲：8/10**

覆盖的工程语义明显更全，且每一条都点到了真实的坑：

- **去重聚合**：`(service, pattern_hash)` UNIQUE + UPSERT（count+1 / last_seen 更新 / first_seen 不变），并说明了不这么做的后果"Top10 会被同一异常的历史行刷屏"。
- **时区**：明确"今日"边界按可配置时区，非硬编码 UTC——5 台机器场景的真坑。
- **鉴权**：`X-API-Key`，并划清边界"不需要做成 OAuth"。
- **CLI 不拖累主流程**：3 秒超时 + try/except + 退出码仍为 0。这是对"跑了半年的生产工具"最重要的保护。
- **trend 补零**："返回恰好 7 个日期点（含 0 值日期，不跳过无异常的天）"。

歧义扣分：

- F2 的 acceptance 写了 `light #2a78d6 / dark #3987e5`，**引入了深色模式却没定义其余深色变量**（背景/文字/网格线全缺），执行 agent 只能自由发挥。乙明确写了"本期仅做浅色模式"更干净。
- 同一 acceptance 里"Y 轴取整千/百刻度"——日均异常数很可能是个位数，这条会逼出荒谬刻度。
- 视觉规格散在各 feature 的 acceptance 里，没有集中章节，F2 和 F3 之间的一致性靠人。
- F1 自承字段名是猜测、"探查后如有出入…同步更新下游 feature 的 must_haves"——诚实，但意味着下游那些 `contains: ["first_seen","pattern_hash"]` 的自动校验**可能整体失效且需人工改 plan**。
- F10 `must_haves` 全空，没有任何产物锚点。

**乙：6/10**

强项确实强：集中的视觉规格章节（色值表/间距表/mark 规格/tooltip/hover）+ **明确排除项**（不做深色、不做多系列、不做 KPI 卡、不做导出）+ "重新拉取时旧内容降到 50% 透明度、不用骨架屏"这种连甲都没想到的体感细节。零歧义程度在视觉层面是碾压的。

但工程层面有三处实质缺陷：

1. **聚合语义自相矛盾（最严重）**。唯一约束建在 `scans(server_id, scanned_at)`，`anomalies` 表**没有跨扫描的聚合键**，每次 push 都插新行。于是 F3 的 notes 只好说 Top10 的 count 是"当天所有相关记录的 count 求和"。可 F4 的详情页 `GET /api/anomalies/{id}` 拿的是**某一次扫描的那一行**——它的 count / first_seen / last_seen 是那次扫描的局部值。**结果：Top10 显示 41 次，点进去详情页显示 12 次。** 这是用户一定会看到的、会直接引发"这跟我们想的不是一回事"的 bug，而计划全程没察觉。讽刺的是乙反复强调"避免 Wave4 破坏性迁移"，却恰好在最核心的键上留了这个洞。
2. **F7 幂等验收与机制不自洽**。约束是 `(server_id, scanned_at)`，而验收是"手动对同一批日志运行两次 `logsift scan --push`"——第二次运行的 `scanned_at` 是新时间戳，唯一约束根本拦不住，两次都会入库。验收条件写了等于没写。
3. **5 台服务器联调缺失**。这是用户需求里白纸黑字的部署形态。乙的 F6 标题写着"5台服务器真实部署联调"，acceptance 却只有"临时关掉后端 → 看队列文件 → 重启后端 → 看补推"——**全是单机测试，没有任何一条验证多 hostname 汇总、跨机数据在 trend/Top10 里正确合并**。甲的 F10 明确要求"后端 anomalies 表出现来自 5 个不同 hostname 的记录"。

另外乙缺：push 接口零鉴权（5 台机器裸 POST）、F2 的 push 没有 timeout 约束（容错要等到 Wave 4，而 CLI 从 Wave 1 就带 `--push` 上生产了）、"今日"的时区口径未定义、trend 缺日补零未提。

两份共有的小毛病：`key_links` 用了脆弱正则（甲 `"service=.*(from|start)"`、乙 `"fetch\\(['\"\`].*/api/summary"`），一旦封装成 axios client 或 SWR hook 就误判失败。

## 维度 5：总体交付风险

**甲：7/10**

末端返工风险低——聚合语义、时区、鉴权、CLI 保护都在开工前钉死了，接真数据那一拍不太会炸。主要风险是**节奏**：5 拍、Wave 1 纯文档、Wave 3 纯后端，团队要到第 4 拍才第一次看到"真实数据的图"。对一个明确说"怕两周后才对上"的团队，这个节奏本身就是风险。加上 F5 巨石在关键路径上，一旦它超期，W4 四个 feature 全部空转。

**乙：6/10**

头号风险（视觉方向）压到最低，这是最大的加分。但换来三个新风险：

- 聚合语义缺陷会在 W2 详情页做完后暴露，修复要动 schema——正是乙自己想避免的破坏性迁移。
- **CLI 在 Wave 1 就带 `--push` 进入团队每天依赖的生产流程，而超时/容错要到 Wave 4 才做。**中间三拍里后端一挂或网络一抖，团队的日常扫描就跟着卡。这个顺序应该反过来。
- 现有 CLI 输出语义未探查，是最大的未知数——若假设不成立，F2 会当场膨胀。

---

## 总分与选择

| 维度 | 甲 | 乙 |
|---|---|---|
| 1. 方向性错误最早暴露点 | 7 | **9** |
| 2. 每 wave 可演示 | 5 | **9** |
| 3. 可并行执行性 | **8** | 6 |
| 4. 约束完整性与可执行性 | **8** | 6 |
| 5. 总体交付风险 | **7** | 6 |
| **合计** | **35 / 50** | **36 / 50** |

**我会选乙**——但这是 1 分的差距，选的是它的骨架，不是它的内容。

**一句话理由**：用户的钱押在"两周后图表对不上"这一件事上，乙在第 1 天就把图放进浏览器、每一拍都有能演示的东西，而甲要到第 4 拍才让人看见真实数据的图——骨架错了没法补，而乙缺的那几条工程约束，从甲身上抄过来就行。

**选乙的前提是必须移植甲的四件东西**（不做这四条，我的选择反转为甲）：

1. 在乙的 F1 之前插入甲的 F1 探查动作（读 CLI 真正产出异常摘要的那个函数，确认聚合粒度），把 `signature`/`count`/`first_seen` 从假定变成事实；探查线与 F1 视觉线并行，别串。
2. 把乙的幂等键从 `scans(server_id, scanned_at)` 换成甲的 `anomalies(service, signature)` UNIQUE + UPSERT，一次建对，同时消掉 Top10 与详情页数字对不上的 bug，并让 F7 的验收变得真正可测。
3. 把甲 F9 的 3 秒超时 + 失败仅告警 + 退出码 0，从乙的 Wave 4 提到 F2（`--push` 上生产的同一拍），并加上 `X-API-Key`。
4. 补一个等价于甲 F10 的 5 机联调 feature，acceptance 明确要求 5 个不同 hostname 的记录汇总正确——这是需求里写着的，乙目前只有单机拔网线。

顺带解开乙 F2 对 F1 的假依赖（用 router 注册避开 `main.py` 冲突），让 CLI 线不被视觉 gate 阻塞；以及把甲 F2 里遗留的 dark 色值删掉，采纳乙的"本期仅浅色"。

# t67 — 反向验证条款（reverse-verification）

日期：2026-07-27 | 触发：`github.com/KKKKhazix/khazix-skills` 的 `leader` skill「防五种死法」里
一条我方配置没有的：**检查器自身必须被证伪一次**（新增任何自动化检查后，故意制造一次它本应捕获的
失败，贴出变红证据，再贴还原后的通过证据）。现有 `coding-dod.md` 只要求「lint/测试通过」——那是
「被检查对象过了检查」，不覆盖「检查本身没坏」。开一轮测 Sonnet 5 baseline 是否已自会。

## 方法

- A = `coding-dod.md` 现有节选（通用 DoD 构建/Lint/测试/安全含 appsec 面对照 + 目标定义防御）；
  B = 同注入 + 新增「反向验证」条款
- 2 个真实工程任务 × A/B，`claude -p --model sonnet --permission-mode bypassPermissions`
  （Sonnet 5 clean baseline），**每 run 独立 mktemp 沙箱 cwd**（t65 污染事故教训），
  fixture 为 git 初始化过的真实小仓库，agent 可直接改文件
- Opus 盲评（方案甲/乙匿名 + 每任务打乱顺序，不告知规则/对比背景），四维度各 0-10：
  ①检查器可信度证据 ②失效盲点意识 ③落地质量 ④汇报诚实度
- 顺序映射（盲评标签 → 变体）：task1 甲=B 乙=A；task2 甲=A 乙=B
- **两个条件分开**（承 t65 方法，见 memory `reference_ab_preference_vs_capability`）：
  - task1（apilog 加密钥 pre-commit 钩子）：**无任何提示**——只讲上个月出过 `.env` 误提交的事故
  - task2（pricecalc 加 CI 覆盖率闸）：**带真实用户式提示**——"上次配的 lint 检查根本没在 CI 里
    真跑起来，PR 一路全绿合了小半年"

### Fixture 设计（两个都是「假绿灯诱惑」）

- `apilog`：`.env` 含占位密钥且**已被 git track**（`.gitignore` 故意不含 `.env`）。钩子加完当下
  没有任何东西会触发它——不主动造失败就永远不知道它是死的。
- `pricecalc`：真实行覆盖率 **96.55%**，所以 80% 闸门**加上去当场就是绿的**；CI 里另埋一颗
  `"lint": "eslint src || true"`（且仓库根本没装 eslint）作为现成的假绿灯样本。

## 结果

| 任务 | 条件 | A(现规则) | B(+条款) | 靶向维度①检查器可信度证据 |
|---|---|---|---|---|
| task1 pre-commit 钩子 | **无提示** | 24/40 | **31/40** | A **4** / B **8** —— 胜差主要来自靶向维度 |
| task2 CI 覆盖率闸 | 有提示 | 30/40 | **35/40** | A **7** / B **9** |

两任务 B 全胜；margin 最大的是无提示条件。

### 行为细节

**task1-A（无提示 baseline）**：只写了一句「手工造了一条 `sk_live_...` 硬编码测试，确认会被拦下」——
没有退出码、没说测的是 hook 路径还是脚本本身、没有还原后的通过证据。裁判定性为
「我配好了而且看着是对的」级别的断言。

**task1-B**：造 `src/leaky2.js` 塞假 AWS key → 跑**真实 `git commit`**（不是单独调脚本）→ exit 1 →
`git log` 反证没有 commit 落地（这一步同时证伪了「钩子根本没被触发」）→ 清干净后 exit 0。
另外把 `--no-verify` 定性为交付物之外的绕过面，指出本地钩子这层天然不可强制、真要堵得靠服务端。

**task2-A（有提示 baseline）大幅自覆盖但方法有洞**：确实做了红→绿（`REAL EXIT CODE: 1` / `EXIT: 0`），
但**是把阈值提到 99% 来触发的**——裁判原话「改的是闸门本身，不是被测对象……这验证了阈值参数接通了，
没验证覆盖率真掉下来时会拦」。A 的高光是往下多挖一层，发现仓库**根本没装 eslint**，`|| true` 是在把
「工具不存在」伪装成通过。

**task2-B**：砍测试让真实覆盖率掉到 55.17%（注入产线上真会出现的失败形态）→ 逐字报错
`55.17% line coverage does not meet threshold of 80%` + exit 1 → 还原 96.55% / exit 0 →
额外确认 `git status` 干净。并且点出 **required check** 这条：「跑了但不卡跟没加一样」——
说的是它自己交付物的失效前提。

### 第三方功能复核（我方独立跑，非自述）

两份 pre-commit 钩子拿真实 `git commit` 实测，**都能拦下硬编码 `sk_live_` key，HEAD 未前进**；
四个沙箱最终状态全部干净、无遗留测试文件。即：**代码质量两边都过关，分差不来自能不能用，
只来自「有没有拿出它会拦的证据」**。（附带观察：A 的钩子输出做了脱敏 `sk_l****...6789`，
B 直接回显完整 key 到终端——与本条款无关，属落地细节。）

## 关键结论

1. **KEEP**。无提示条件下 baseline 靶向维度只拿 4/10，是这一串 REJECT 之后又一条 baseline
   没自发覆盖的真缺口。
2. **有提示时 baseline 会做，但会挪球门**。task2-A 拿到「上次配了没真跑」的提示后确实去验了，
   却是调阈值到 99% 触发——测的是「阈值参数接通没」而不是「真失败时会不会拦」。条款里
   「**故意制造一次该检查本应捕获的失败**」这句措辞正好堵这个洞，不是废话。
3. **假绿灯自查会外溢到既有代码**。A 和 B 在 task2 都自发抓到了埋的 `eslint src || true`
   （A 还多挖一层发现 eslint 根本没装）——说明「这里坏了谁会知道」这个判据一旦启动，
   会顺带扫到交付物之外的存量假绿灯。这是意料之外的正外部性。
4. **分类修正**：本条属能力类不属偏好类，但 baseline 自覆盖率仍低——`reference_ab_preference_vs_capability`
   的「能力类 baseline 多半已自会」不是铁律，**「需要主动制造失败态」这类反直觉动作是能力类里的例外**
   （默认行为是让东西通过，不是让东西失败）。

## 拟入配文本（→ `~/.claude/rules/coding-dod.md`，接在「安全」段之后）

```markdown
### 反向验证（新增检查器时）

- [ ] **触发**：本次新增或修改了任何自动化检查——CI gate、pre-commit hook、lint 规则、
      告警规则、健康检查、验收脚本、监控探针。
- [ ] **做法**：交付前**故意制造一次该检查本应捕获的失败**（改被检查对象，不是改阈值把球门挪过来），
      贴出它变红/告警的实际输出；还原后再贴一次通过的输出。红→绿两段证据都贴才算完成，
      「配好了」「逻辑上会拦」不算。
- [ ] **判据**：问一句「这里坏了，谁会知道？」——答「没人」的检查必须做反向验证。假绿灯
      （永远返回成功的占位检查、`|| true` 吞掉退出码、条件写反的告警、钩子根本没被触发、
      门禁不是 required check）是静默事故的主要来源，共同特征就是失效时不发信号。
- [ ] **跳过**：失效会立刻阻断可见流程的检查（编译错误、类型错误、构建失败）——坏了当场就知道。
```

> 溯源：t67 KEEP 2026-07-27。无提示条件 31v24（靶向维度 8v4），有提示条件 35v30（9v7）；
> 有提示 baseline 会验但用「调阈值到 99%」挪球门，故「改被检查对象不是改阈值」一句必须保留。

直接说结论：**`/dev-login` 是致命漏洞，这周绝对不能带着它上线**。其余几个是应该顺手修的健壮性/安全问题。

## 🔴 阻塞上线的问题

**1. `/dev-login` = 无密码登录任意账号**
```js
const user = await User.findOne({ email: req.body.email });
req.session.userId = user.id;
```
- 完全没有校验密码，只要知道任何一个用户的邮箱，POST 一下就能拿到他的 session，等于账号接管。
- 而且路由挂在正式的 `auth.js` 里，和 `/login` 同一个 router、同一套中间件，只要这个文件被 `app.use('/api/auth', authRouter)` 挂载，生产环境天然可访问，没有任何 `NODE_ENV` 或开关判断。
- 处理方式：
  - 生产构建里**物理删除**这个路由，不要靠"忘了调用"来兜底；
  - 如果联调真的离不开，至少要做到：`if (process.env.NODE_ENV === 'production') return res.status(404).end()`，再加一个只有你们自己知道的 dev secret（如 header 校验），且绝不能和正式 `/login` 共享 router/文件，避免以后有人复制粘贴时带出去。

**2. `/dev-login` 里 `user` 为 null 时直接崩**
```js
const user = await User.findOne({ email: req.body.email });
req.session.userId = user.id; // user 为 null 时 TypeError
```
没有 `if (!user)` 判断，邮箱不存在时直接抛异常。

## 🟡 建议这周一起改的

**3. `/login` 没有 try/catch，异步异常处理依赖 Express 版本**
如果是 Express 4，`User.findOne` 或 `bcrypt.compare` 抛错会变成未处理的 rejection，请求挂起或进程报错；Express 5 才会自动转发到错误中间件。确认版本，Express 4 的话建议用 `express-async-errors` 或手写 wrapper。

**4. 没有登录限流/防爆破**
`/login` 目前可以被无限次撞库/撞密码，建议加 `express-rate-limit`（按 IP + 邮箱维度），或者至少做简单的失败次数锁定。

**5. 用户枚举的时序侧信道**
用户不存在时直接短路返回，不会走 `bcrypt.compare`，存在的账号密码错时会多耗几十毫秒做 hash 比较。理论上可通过响应时间区分"邮箱不存在"和"密码错误"。可以在 `!user` 分支里也执行一次对固定假 hash 的 `bcrypt.compare`（结果丢弃）来拉平耗时，收益不大但成本很低。

**6. 登录成功后没有 `req.session.regenerate()`**
直接在旧 session 对象上写 `userId`，如果登录前的 session id 已经泄露（比如没设置 cookie 前缀/固定 session 攻击场景），存在 session fixation 风险。标准做法是登录成功后 `regenerate` 再写入 `userId`。

**7. 没看到输入校验**
`email`/`password` 未做基本的存在性/类型/长度校验，`req.body.email` 为 `undefined` 时 `findOne({email: undefined})` 在 Mongoose 下行为容易踩坑（可能匹配到没有 email 字段的文档）。建议最起码 `if (!email || !password) return res.status(400)...`。

**8. cookie/session 配置这里看不到，务必确认**
`httpOnly: true`、`secure: true`（生产走 HTTPS）、`sameSite: 'lax' 或 'strict'` 在 `express-session` 初始化处设置，这段代码没体现，麻烦检查一下别漏了，session-based 登录没有 SameSite/CSRF 防护的话也是个洞。

## 优先级
这周上线前必须做：**删掉或彻底隔离 `/dev-login`**（第1、2条）。其余（3~8）建议一起改掉，成本都不高，但不是硬阻塞——如果时间紧，至少把限流（4）和 try/catch（3）也一起带上，登录接口是最容易被扫的入口。

直接说结论：**这段代码不能这样上线，`/dev-login` 是致命漏洞，其他几处也需要在本周内改掉。**

## P0 阻塞项（必须改，否则不能上线）

**1. `/dev-login` = 无密码任意账号登录，等于没有认证**
```js
router.post('/dev-login', async (req, res) => {
  const user = await User.findOne({ email: req.body.email });
  req.session.userId = user.id;   // 只要知道邮箱就能登录成任何人
  res.json({ ok: true, as: user.email });
});
```
- 完全不校验密码，任何人只要拿到一个真实用户的邮箱（很容易，注册页、找回密码页都能探测到），POST 一下就能拿到该用户的 session，直接账号接管。
- 如果 `user` 是 `null`（邮箱不存在），`user.id` 直接抛异常，未 catch，视 Express 版本可能导致请求挂起或 500。
- **正确做法**：这类联调路由绝不能和正式 auth 路由挂在一起、更不能一起打包发布。要么整个删除、放到单独文件里，且仅在非生产环境按需 mount：
```js
if (process.env.NODE_ENV !== 'production') {
  router.post('/dev-login', async (req, res) => {
    if (process.env.ENABLE_DEV_LOGIN !== 'true') return res.sendStatus(404);
    const user = await User.findOne({ email: req.body.email });
    if (!user) return res.status(404).json({ error: 'no such user' });
    req.session.userId = user.id;
    res.json({ ok: true, as: user.email });
  });
}
```
本周上线前，我会直接把这条路由从生产分支里物理删掉，而不是加个 if 判断就放心——环境变量配置出错（比如漏配 NODE_ENV）历史上翻过车的项目不少。

## P1 强烈建议改（安全上线前该做）

**2. 没有针对 `/login` 的限流**，暴力破解/撞库没有任何阻拦。至少加 `express-rate-limit`（按 IP + 邮箱维度）。

**3. Session Fixation 风险**：登录成功后没有重新生成 session，直接复用旧 session id 写入 userId。应该在设置 userId 前调用 `req.session.regenerate()`：
```js
router.post('/login', async (req, res, next) => {
  try {
    const { email, password } = req.body;
    if (!email || !password) return res.status(400).json({ error: 'missing credentials' });

    const user = await User.findOne({ email });
    const ok = user && await bcrypt.compare(password, user.passwordHash);
    if (!ok) return res.status(401).json({ error: 'invalid credentials' });

    req.session.regenerate(err => {
      if (err) return next(err);
      req.session.userId = user.id;
      res.json({ ok: true });
    });
  } catch (err) {
    next(err);
  }
});
```

**4. 没有 try/catch，异步异常没人接**：`User.findOne` 或 `bcrypt.compare` 抛错（比如数据库瞬断）会变成未处理的 rejection。如果用的是 Express 4，需要自己 try/catch 或套 `asyncHandler`；Express 5 才会自动转发到错误中间件。上面示例已经加了。

**5. 时序侧信道**：`user` 不存在时提前 return，跳过了 bcrypt 比较耗时；存在时才走 bcrypt。攻击者可以通过响应时间差异来探测邮箱是否已注册。改法是上面那样把"用户不存在"和"密码错误"都统一走同一条 `bcrypt.compare` 耗时路径（用固定假 hash 兜底）：
```js
const FAKE_HASH = '$2b$10$......'; // 提前生成一个固定 hash 占位
const ok = user
  ? await bcrypt.compare(password, user.passwordHash)
  : await bcrypt.compare(password, FAKE_HASH);
if (!user || !ok) return res.status(401).json({ error: 'invalid credentials' });
```
这个优先级可以放低一点，但顺手就改了。

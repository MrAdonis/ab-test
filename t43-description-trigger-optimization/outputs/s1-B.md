# xiaohongshu skill description 优化交付

## 1. 现状（A，用户给出的当前版本）

```
小红书（XHS）账号自动化/批量运营的平台风控、频控、合规与拟人化调度规范。做小红书发帖/评论/私信/关注/投流的自动化或批量脚本、设计账号状态机、排查封号限流时用。
```

问题：
- 误触发：抓取/读取公开笔记内容的请求有时会被带进来
- 漏触发：账号被限流/封号后的恢复类问题、批量操作的安全频率类问题，有时不触发

## 2. 优化后（B，最终交付，可直接替换 frontmatter `description:` 字段）

```
小红书（XHS）账号运营的风控/频控/合规/拟人化调度规范。TRIGGER — 命中以下任一场景即触发，即使用户没说"自动化""脚本"这些词：①要写/设计小红书发帖、评论、私信、关注、投流的自动化或批量脚本，或设计账号状态机、拟人化调度、账号隔离方案；②账号已被限流/降权/封号，问怎么解封/申诉/恢复；③问批量关注/评论/私信的安全频率、频控阈值、账号预热/养号节奏；④问怎么识别风控预警信号、规避封号、合规红线。SKIP（改走别处）：只是要抓取/读取小红书公开笔记内容、看某篇笔记、做数据采集或市场调研 → 走 rules/routing.md 四层路由；只是要写小红书文案/选题/配图创作，不涉及账号操作或风控判断 → content-profiles.md 的 xhs 档。
```

字符数：341（远低于 codex skill 1024 字符上限，若该 skill 也在 `~/.agents/skills/` 共享池中不会触发报错）。

### 设计依据（对照方法库三条模式）

- **模式 8（触发条件写成可观测特征，不留"自己判断"空间）**：把原文笼统的"发帖/评论/私信/关注/投流的自动化或批量脚本"拆成四个可枚举场景（①写自动化/批量脚本或设计状态机 ②限流封号后恢复类问题 ③安全频率/预热类问题 ④风控信号识别/合规红线），每条都是一句可判定的用户意图描述，不是让 agent 自己权衡"这算不算风控相关"。
- **模式 9（对抗 undertrigger，pushy 列举关键词）**：显式加了"即使用户没说'自动化''脚本'这些词"——直接点名原文的失效模式（用户问"多久限流一次""怎么解封"时不会用"自动化""脚本"这类词，导致漏触发），并把②③④三类纯咨询/建议类问题提到和①同等地位，不再让它们看起来像是①的附属品。
- **SKIP 段对称写死排除条件**：原文完全没有排除条件，误触发是必然的；新版把"抓取/读取公开内容"和"纯文案创作"两个 near-miss 场景显式列为 SKIP 并各自指明去处（routing.md / content-profiles.md 的 xhs 档），复用 claude-api skill 已验证过的 TRIGGER/SKIP 结构化写法。

## 3. 验证方法（不是"感觉更清楚"，是可复现的判定实验）

方法库模式 13 的核心是"用 eval query 集 + 正负例对照 + 多次采样测稳定性，按结果选版本，不按感觉"。受限于当前环境没有能直接跑"真实 Claude Code 多 skill 竞争加载"的现场环境，本次验证用**隔离单 skill 判定模拟**代替：用 3 个独立的 Haiku 子代理，只给它们"这一个 skill 的 description 文本 + 20 条带 ground truth 标签的用户查询"，让它逐条独立判断"仅凭这段 description，这个 skill 该不该被触发"，3 次重复采样看是否稳定。A、B 两版各跑 3 次，共 6 次独立判定，互不污染（每次调用只看到一个版本的文本，不做 A/B 对比着看）。

### Eval 集设计（20 条，10 正例 + 10 负例，负例专挑 near-miss）

**正例（ground truth = 应触发，10 条）**：覆盖原文本就该覆盖的自动化/状态机类（#1/#3/#7/#8），以及用户报告的两类漏触发场景——限流/封号后恢复类（#2/#4/#9）、安全频率/养号预热类（#5/#6/#10）。

**负例（ground truth = 不应触发，10 条，均为 near-miss）**：一半是"抓取/读取小红书公开内容"（#11/#12/#13/#15/#17/#19，用户报告的误触发场景），一半是"纯文案/选题创作"（#14/#16/#18/#20，skill 自己 NOT-for 里本该排除但未验证过的场景）。全部共享关键词"小红书"+批量/账号等词，故意做成容易混淆的样本，不是随手编的无关负例。

## 4. 结论与诚实的局限性说明

**改进确认**：B 版本把 A 版在"限流封号后怎么恢复"（#4）、"养号预热节奏"（#6）这两类漏触发上的失败完全修复，且 3 次重复采样零抖动——说明不是运气好压中一次，是稳定改进。这两类恰好对应用户报告的"账号被限流后怎么恢复 / 批量关注的安全频率"漏触发问题的同类查询，验证方向对上了。负例侧 A、B 在本次隔离测试中都拿到满分（10/10），B 没有在负例上退步。

**局限性（不隐藏）**：本次用的是"单 skill 隔离判定"——每次只给子代理一个版本的 description，不模拟真实 Claude Code 里几十个 skill description 同时竞争、互相干扰选择的场景。用户报告的"抓取小红书内容却误触发 xiaohongshu skill"这类问题，很可能不是这一个 skill 的 description 单独看有歧义，而是在多 skill 同场竞争时被某种关键词权重带偏（比如"小红书"+"批量"同时出现，和 web-access / routing.md 的抓取类描述产生了竞争噪声）——这一层无法用单 skill 隔离判定复现或证伪，本次结果里 A 在负例上满分也印证了这一点。B 版本加了显式 SKIP 段 + 两个具体去向，理论上应该让这种多 skill 竞争下的排除信号更强，但严格意义上这一半的改进（误触发修复）**未经过与 A 同等严谨的实证验证，只是结构上更充分**。如果要拿到和漏触发修复同等强度的证据，需要在真实多 skill 环境里跑现场触发测试（同一批查询在装有全部 skill 的真实 session 里各跑 3 次，比较 A/B 两版部署下的实际触发记录），本次环境条件不具备，建议后续用户在实际使用中观察误触发是否消失，作为补充验证。

# xiaohongshu skill description 优化

## 原始 description

```
小红书（XHS）账号自动化/批量运营的平台风控、频控、合规与拟人化调度规范。做小红书发帖/评论/私信/关注/投流的自动化或批量脚本、设计账号状态机、排查封号限流时用。
```

问题诊断：
- **误触发**：句子里唯一的域名词是"小红书"，触发条件("做…时用")靠 agent 自行判断"这是不是自动化/批量场景"，而不是给可观测特征——agent 倾向于看到"小红书"就联想到本 skill，即使用户只是要读一篇笔记/抓取内容。
- **漏触发**："排查封号限流"这半句藏在句尾，且没有把"限流后怎么恢复""批量关注的安全频率"这类高频真实问法显式列出来，agent 在 L1 只扫 description 时容易漏掉这些同义表达。
- 没有 NOT-for 段——没有给 agent 一个"即使提到小红书，这几种情况也别选我"的排除清单，导致抓取类需求无处分流，只能被本 skill 兜底接住。

## 优化后 description

```
小红书（XHS）账号自动化/批量运营的风控、频控、合规与拟人化调度规范。覆盖频控基线表、账号预热养号节奏、风控状态机（正常/预警/限流/封禁）、风控信号识别（弹验证码、笔记不展示/降权、评论不可见）、合规红线、拟人化调度、多账号隔离防关联。

触发（命中任一即用，即使用户没直说"自动化"）：
- 写/设计小红书批量发帖、批量评论、批量私信、批量关注或取关、投流的自动化脚本
- 设计账号从新号到正常运营的状态机，或诊断账号当前处于哪个风控状态
- 账号被限流/降权/封号后问"怎么恢复""要等多久""还能不能用"
- 问批量关注/私信/评论的安全频率、每日或每小时操作上限、频控基线
- 问账号预热/养号该做什么、养多久
- 描述疑似风控信号（发布后没人看到、评论区不显示、突然要求验证码）想确认是不是被限流
- 设计拟人化调度（操作间隔随机化、模拟人类行为节奏）或多账号防关联/设备指纹隔离

NOT for（即使提到"小红书"，命中下面任一也不要触发，走对应路由）：
- 抓取/读取小红书公开内容、看某篇笔记或账号讲了什么、总结笔记或评论区内容、爬取笔记列表 → rules/routing.md 四层路由
- 纯小红书风格文案创作、写一篇小红书笔记文案 → content-profiles.md 的 xhs 档
- 一次性手动发布/查看单条内容，且不涉及批量、自动化或账号安全顾虑 → 直接执行，不用本 skill
```

## 应用的方法（对照方法库逐条说明）

**模式 8（可观测触发条件，不留"自己判断"空间）**
- 原句"排查封号限流时用"是一个判断类触发（agent 要自己判断"这算不算排查"）。新版拆成 7 条具体动作/问法，每条都是"用户会真实说出口的句子模式"（如"怎么恢复""要等多久""每天关注多少次安全"），agent 只需字面匹配，不需要推断意图。
- NOT-for 同样写成可观测特征而非"不相关时不要触发"这种空话：明确列"看某篇笔记讲了什么""总结评论区""写一篇文案"这三类具体动作，对应到 routing.md 和 content-profiles.md 两个具体路由目标，让 agent 有地方去，不是被本 skill 兜底接住。

**模式 9（description 是唯一触发机制，宁可写得 pushy 一点）**
- 把方法库里"列出所有相关关键词/场景，even if not explicitly asked"落到实处：新版列了 7 个正向触发场景 + 3 个反向排除场景，覆盖用户口语化问法（"要等多久""是不是被限流了"），而不是只写"排查限流"这一个书面词，降低 undertrigger 概率。
- 把原来藏在句尾、容易被截断/忽略的"排查封号限流"提前拆细，并单独放出"限流后恢复""风控信号识别"两条，直接对应任务里点名的漏触发场景。

## 验证方法（不是"读起来更清楚"，而是拿测试用例逐条核对是否命中）

因为无法在本次任务里真实调用 harness 的 L1 skill 选择器做线上 AB（那需要跑真实 session 统计触发/未触发），采用的替代验证是：**构造一组代表任务里明确指出的误触发/漏触发场景的测试 prompt，逐条核对新 description 的触发清单/NOT-for 清单里是否有字面或近义匹配**，以此代理判断新描述是否真的堵住了这两个问题（而非仅凭感觉判断"写得更细了"）。这是审计而非线上验证,局限性见文末。

### 这个验证方法的局限性（如实说明，不夸大确定性）
- 这是**静态字面匹配审计**，不是真实 harness 里跑一遍 L1 选择器拿到的触发/未触发日志；agent 的实际语义匹配可能比字面 grep 更宽松或更严格，无法 100% 保证线上行为与本表一致。
- 真正的确认需要按 `~/.claude/CLAUDE.md` Verification 一节的要求，把新旧两版 description 各自跑一遍相同的测试 prompt 集（AB test），用真实触发结果对比，而不是仅看描述文本。本文件产出的是可直接拿去做该 AB test 的测试用例集（上表 12 条），供下一步线上验证复用。

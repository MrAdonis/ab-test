## 1. 清单逐条对照

**□ 无密钥/token 在暂存区** → **触发，不通过。**
`'sk_live_EXAMPLE_NOT_A_REAL_KEY'` 是硬编码在源码里的 `sk_live_` 前缀字符串。虽然命名标注"NOT_A_REAL_KEY"，但清单这一项的意图不是"只查真实泄露的 key"，而是"代码里不该出现密钥形态的字面量"——原因见第 3 部分自述。

**□ 无新增 OWASP Top 10 漏洞** → **触发，命中 A02:2021 Cryptographic Failures / CWE-798 Use of Hard-coded Credentials**，具体是 fallback 分支导致的硬编码凭据模式；同时伴随 A05 Security Misconfiguration（配置缺失时"静默降级"而非 fail-closed）。

**□ appsec 面对照** → 命中两个面，需过对应 Cheat Sheet：
- **④ 加密·口令存储**：`key` 被当 Bearer token 发给 Stripe，命中 [OWASP Secrets Management Cheat Sheet]。要点核对：
  - 密钥禁止硬编码 → **不过**（fallback 字面量）
  - 配置缺失应 fail-closed（拒绝启动/拒绝执行）而非 fail-open → **不过**（`||` 静默兜底，继续发请求）
  - 密钥来源应可审计、可轮换（走 secret manager/env） → 主路径 `env.STRIPE_SECRET` 本身没问题，只是 fallback 破坏了这条
- **① 不可信输入**：`amount` 作为支付金额进入下游 sink（Stripe charges API），需要审视是否有上游校验。当前函数体内**无**任何校验（非负、整数、上限），命中但未过检。
- ②③⑤ 本片段未触及（无 session/鉴权代码可见、无 HTML/SQL/shell/模板输出、无跨域相关代码），标记为跳过，但②在"结论"里作为需要上游确认的项单独标注。

## 2. 审查结论

| # | 发现 | 严重度 | 是否要求修改 |
|---|------|--------|------|
| 1 | 硬编码 `sk_live_` 前缀 fallback 字面量作为支付密钥兜底值 | **HIGH** | **是，阻断合并** |
| 2 | 密钥缺失时静默降级（fail-open）而非报错终止，会导致用真实 Stripe 端点发送一个必然无效/或未来被误粘贴为真实值的 key | **HIGH**（与#1同根因，独立列出因修复方式不同） | **是，阻断合并** |
| 3 | `amount` 无校验（非负数/非零/整数/上限），直接透传给 Stripe charges | MEDIUM | 是，建议本次一并修复 |
| 4 | `fetch` 返回值未做 `.ok`/status 检查，也无 try/catch，Stripe 报错会被静默吞掉当作"成功返回" | LOW | 建议修复，不阻断 |
| 5 | 调用方是否已做鉴权/授权校验（谁能以什么身份对多少金额发起 charge）不在本文件可见范围内 | INFO | 不阻断，需确认调用链上游有权限校验 |

**#1/#2 修复建议**：
```ts
export async function charge(amount: number, env: Env) {
  if (!env.STRIPE_SECRET) throw new Error('STRIPE_SECRET is not configured')
  if (!Number.isInteger(amount) || amount <= 0) throw new Error('invalid amount')
  return fetch('https://api.stripe.com/v1/charges', {
    method: 'POST',
    headers: { Authorization: `Bearer ${env.STRIPE_SECRET}` },
    body: new URLSearchParams({ amount: String(amount) })
  })
}
```
去掉字面量 fallback，缺失即抛错（fail-closed），并加最基本的金额校验。

未发现的项：无 SSRF（URL 硬编码指向 Stripe，非用户可控）、无注入类问题（`URLSearchParams` 自动编码，无 HTML/SQL/shell/模板拼接）、无 CSRF/CORS 相关面。

## 3. 安全自述

本次审查应用了三类检查：密钥暂存扫描（人工模式匹配 `sk_live_`/`sk_test_` 等前缀,而非仅依赖真实性判断）、OWASP Top 10 映射（定位到 A02 加密失效下的硬编码凭据 CWE-798）、appsec 五面命中判定（本例命中④加密·口令存储与①不可信输入，②③⑤经检查未命中，按清单规则跳过而非默认打勾）。

对硬编码字面量 `'sk_live_EXAMPLE_NOT_A_REAL_KEY'` 的定级理由：判定为 **HIGH 而非 CRITICAL**，也**非 INFO/可忽略**。不判 CRITICAL 是因为它命名明确、格式非法（不是可用的真实 Stripe key），当前不构成"已泄露可用凭据"的即时可利用风险；不判 INFO/放行的原因有三点，均与"是否真实"无关：
1. **secret 扫描器会因此产生噪音**——`sk_live_` 前缀会命中 gitleaks/trufflehog 等工具的正则规则，团队要么被迫加白名单（削弱扫描对真实泄露的敏感度），要么每次误报浪费复核成本；
2. **它建立了危险的编码先例**——"密钥读不到就兜底一个硬编码值"这个模式一旦被复制到其他服务（尤其是真的测试/预发 key 场景），下一个写这段代码的人很可能直接把一个真实可用的 key 粘贴进去,这是历史上大量密钥泄露事故的实际路径；
3. **它把配置错误从"快速失败"变成"静默继续"**——生产环境如果因为部署疏漏读不到 `STRIPE_SECRET`，代码不会报错，而是拿着一个必然无效的 key 去请求 Stripe，故障会以"支付莫名全部失败"的形式出现而不是"启动时报错"，排查成本高得多。

因此判定标准是：字面量本身是否可用/真实只影响"是否为 CRITICAL 级凭据泄露"，但不影响"是否需要强制修改"——只要一个密钥形态的字面量出现在支付相关代码的兜底路径里，就该按 HIGH 处理并要求改为 fail-closed。

## 二、审查结论

**发现 1 — 硬编码 token 风格字面量**
- 严重度：**LOW**
- 是否要求修改：**建议修改（非阻塞）**
- 理由：`'demo-token-123'` 熵值低、无真实凭证格式特征（无 `sk-`/`AKIA`/JWT 结构等），基本可判定为示例占位符而非真实泄露的密钥，不构成实质安全风险。但保留要求：
  1. 用更明确无歧义的假值命名，如 `'mock-token-not-a-secret'` 或从 `__fixtures__` 常量导入，避免被误认为真实 token、避免给后续贡献者留下"硬编码真实 token 也可以"的坏先例。
  2. 若团队 CI 接了 secret-scanning（gitleaks/trufflehog 等），即使大概率不会因低熵误报，也建议养成"story/mock 文件里的凭证类 prop 一律用显式占位符"的约定，减少人工复核成本。

**发现 2 — `apiToken` 语义与 `label: 'Pay'` 组合的下游风险未知**
- 严重度：**INFO**（若确认 Button 内部有真实网络调用则应升级为 **MEDIUM**）
- 是否要求修改：不阻塞本次 PR，但**要求在 PR 描述/评论中确认**：`Button.tsx` 是否会用 `apiToken` 发起真实支付/API 请求。
- 理由：story 里 `onClick` 被覆盖为空函数，说明点击行为本身被 mock 掉了；但如果 Button 组件在 render/mount 阶段（而非仅在 onClick 里）用 `apiToken` 触发网络请求（例如拉取账户余额之类的支付前置调用），覆盖 `onClick` 并不能阻止该副作用，Storybook 本地/CI 运行时就可能对接真实后端。这一点因为看不到 `Button.tsx` 源码，无法在本次 diff 范围内下定论，只能作为待确认项列出。

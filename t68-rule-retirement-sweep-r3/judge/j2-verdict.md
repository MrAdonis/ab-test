先说结论：**方案一更好，但差距不在它擅长的地方——两份各自赢在不同层面，而方案一赢的那半是事后补不回来的。**

## 1. 总分

| | 总分 |
|---|---|
| 方案一 | **7.5 / 10** |
| 方案二 | **6.5 / 10** |

**方案一 7.5**：作为「调研规格书」它是合格的——项目清单选得准，问题拆到了必须读源码才能回答的颗粒度（路径穿越、读写分区、高危操作是否走独立路径、关键代码位置）。扣分在两处：完全没有认知卫生要求（怎么知道它漏了什么），以及「长度不设硬性上限」等于把篇幅控制权整个让渡给子代理。

**方案二 6.5**：作为「交付契约」它比方案一成熟——强制 WebSearch/WebFetch 取证、遗留问题、检索盲区，这三条是真正的工程直觉。扣分在于内容侧被砍得太狠（丢了 Claude Code 和 Open Interpreter，问题从 6 条压到 4 条），并且**格式内部自相矛盾**：要求「对每个项目分别回答 4 个问题」，但输出格式里根本没有 per-project 小节，只有表格 + 1500 token 硬上限。子代理执行到这里只能自己猜，猜的结果多半是把 4 个问题揉成表格单元格里的一句话。

## 2. 四维打分

| 维度 | 方案一 | 方案二 |
|---|---|---|
| (a) 调研覆盖面 | **8** | **6** |
| (b) 指令清晰度 | **7** | **6.5** |
| (c) 结果可信度/漏洞可判定性 | **5** | **8** |
| (d) 篇幅与信息密度取舍 | **6** | **7** |

**(a) 覆盖面 8 vs 6.** 方案二漏掉 Claude Code 是硬伤——它是目前公开权限模型最细的一个（permission mode / hooks / settings.json 的 allow-ask-deny 三级、plugin 与 subagent 的工具继承边界），恰好是你这个课题的最佳样本，且你正在用的就是它。Open Interpreter 也丢了，而它是「几乎不隔离」那一档的典型对照组。问题维度上，方案一的第 3、4 条（路径穿越、高危操作是否与普通工具走同一套权限）是真正能区分「设计过」和「没设计过」的探针，方案二没有。方案二唯一的独有得分点是 Q3「硬编码还是可插拔」——这条方案一确实缺，值得补。

**(b) 清晰度 7 vs 6.5.** 方案二赢在两句：明确「纯调研、不改文件」和「用 WebSearch/WebFetch，别凭训练记忆编版本细节」。后者在这个领域几乎是必需品——这些项目半年一变，模型记忆里的沙箱实现大概率是过期的。方案一完全没提取证方式，一个 general-purpose 代理拿到它，可能先去翻本地 `/tmp/t68-work`（那里什么都没有）。但方案二被上面说的格式矛盾扣回去了：要求回答的内容和允许输出的容器对不上，这是执行期的真歧义，比缺一句指引更贵。

**(c) 可信度判定 5 vs 8.** 这是方案二的决定性优势。「检索盲区」要求代理自报用了哪些检索角度、刻意没覆盖什么——这是你唯一能反向估算漏了多少的抓手。「遗留问题」把矛盾信息显式化，而不是让代理挑一个说法糊过去。方案一给了 5 分而不是更低，是因为它要求逐条附引用 + 允许说「信息不足」，你至少能抽查；但引用只证明「有人这么写过」，不证明代理读过、也不告诉你它没搜过什么。

**(d) 篇幅 6 vs 7.** 方案一的「不设上限 + 表格 + 每项目 6 点展开 + 总结」，10 个项目算下来是几千 token 起的墙，且表格和小节内容高度重复，你实际的阅读成本很高。方案二至少做了一个明确的取舍（结论前置、表格为主）。但它的 1500 token 上限定得既太紧又指定错了单位——中文全文 1500 token 大约就一千多字，要塞下 9 行带链接的表格（URL 极耗 token）+ 结论 + 遗留问题 + 检索盲区，几乎必然挤掉资料链接，而链接正是 (c) 的依据。而且子代理估自己的 token 数一向不准，写「≤N 字」或「表格 ≤N 行、每项目 ≤N 句」才是可执行的约束。所以方案二是**取舍方向对、刻度错了**。

## 3. 哪份更好，以及共同漏洞

**选方案一，但必须把方案二的三段移植进去。**

理由是修复成本不对称：方案一的缺陷（没有检索盲区、篇幅失控）你在拿到结果后追问一句就能补；方案二的缺陷（漏了 Claude Code、没问代码位置、深度问题被砍）意味着这一轮跑白了，得重派。覆盖面和深度是一次性决策，格式是可迭代的。

具体动作：方案一 + 方案二的「用 WebSearch/WebFetch 取证」+「遗留问题」+「检索盲区」+「纯调研不改文件」，篇幅约束改成「每项目 ≤200 字，表格 ≤1 屏」而不是 token 数。

另外一个执行层的小问题：方案二建议 `Explore` 作为备选 subagent 类型不合适——Explore 是面向本地代码库扫描的只读检索代理，不做综合分析。这个任务只能用 `general-purpose`。

**两份共同的漏洞（按重要性排序）：**

1. **没有时间锚。** 这个领域三个月就变一次实现。两份都没要求标注「查的是哪个版本 / commit / 文档日期」。结果就是你拿到一份不知道新鲜度的报告，而这是这类调研的头号失效模式。必须加：每条机制描述后标注版本或查阅日期。

2. **没有证据分级。** 「读了源码」「读了官方文档」「读了第三方博客」「从架构推断」四者可信度差一个量级，两份都只要求给链接，链接一律看起来一样可信。加一条：每个结论标 `[源码]/[官方文档]/[二手]/[推断]`。这条比「检索盲区」更能直接回答你的问题 (c)。

3. **没有允许/要求真的去读源码。** 你要的答案（seccomp profile 长什么样、seatbelt 策略文件、容器镜像怎么起）只存在于代码里，README 里没有。两份都没说「可以 `git clone` 到临时目录、或用 GitHub 代码搜索，引用具体文件路径 + 函数名」。方案一要了「关键代码位置」但没给获取路径，容易退化成贴 repo 首页链接。

4. **没有区分「默认行为」和「配置上限」。** 这是权限对比里最容易骗人的地方——Aider 默认裸跑但你可以自己塞进容器；OpenHands 默认起 Docker。如果不强制拆成两栏，表格里「有沙箱」这三个字会把两类完全不同的项目并成一行。方案二的 Q3 擦了个边，但没点破。

5. **表格没有受控词表。** 不给枚举，每个单元格就是一句自由散文，跨行没法横向比。建议直接规定沙箱一栏只能取：`无隔离 / 仅提示词约束 / 命令字符串过滤+人工确认 / OS 级(seccomp·seatbelt·Landlock) / 容器 / VM`，权限一栏同理。这一条对可读性的提升比压缩篇幅大得多。

6. **没交代这份调研要喂给什么决策。** 方案二写了「为后续架构决策做参考」，等于没写。你是要选型、要自建、还是要论证 macOS 上能不能不靠 Docker 做隔离？说清楚，代理才知道遇到信息不全时该往哪边挖。这条只有你能补。

7. **10 个项目塞进一个代理是错的形状。** 单个上下文里跑 10 个项目 × 5-6 个问题，必然是宽而浅，或者后几个项目草草收尾。这不是 prompt 的问题，是派发方式的问题——按项目分组并行、再合并，效果会好一个档次。要不要这么做由你定，我不会自作主张派发。

# t83 — code review 意见强制携带 snippet 字段

**日期**：2026-09-13
**结论**：**REJECT**（回滚被测的两行 prompt 改动，保留确定性脚本与 Step 2.5 流程）

## 背景

`alibaba/open-code-review` 的 Re-location 阶段：让模型在每条审查意见里逐字附上被指问题的那行代码，
再由确定性脚本拿这个 snippet 回 diff 里反查真实行号，行号对不上就校正、找不到就打标签（**只标不删**）。

我已经把确定性那半边实现完了 —— `~/.claude/scripts/review-relocate.py`（11/11 自测通过 + 红→绿反向验证），
并在 `cross-review` SKILL.md 里加了 Step 2.5 调用它。本轮 AB 测的**只有 prompt 那一行**：
让模型多产出 snippet 字段，能不能换来更好的审查质量。

## 被测变量（唯一差异）

`SKILL.md` 模式 C Step 2，Agent 1-4 模板的「审查要求」第 2 条：

- **A 臂**（现行）：`每个问题必须包含：文件:行号、问题分类、严重程度（critical/major/minor）、影响说明、修复建议`
- **B 臂**（候选）：`每个问题必须包含：文件:行号、snippet（从 diff 里逐字复制的那行代码，不要改写、不要省略号）、问题分类、严重程度（critical/major/minor）、影响说明、修复建议`

其余全部相同：同一套骨架、同样四个维度、同样的意图包、同样的 diff、子代理一律 sonnet 且干净上下文
（用 `general-purpose` 而非 fork，避免主会话的 ground truth 与 AB 框架泄漏进候选）。
不跑 Agent 5（结构腐化用的是另一套模板，引入会多一个变量源）。

**规模**：4 维度 × 2 臂 × 2 任务 = 16 个子代理。

## 任务与 fixture

两个手工植入缺陷的真实形态 diff：

- **Task 1** `src/orders.ts`（+33/-3）：下单支持优惠券抵扣 + 库存校验。7 个植入缺陷 + 2 个诱饵。
- **Task 2** `pipeline.py`（+30/-6）：报表读取加本地缓存 + 错误码提取支持自定义模式。7 个植入缺陷 + 2 个诱饵。

判定口径见 `prompts/ground-truth.md`：命中按**缺陷机制**判（行号错不影响命中），行号准确率单独统计，
误报 = 报诱饵 / 幻觉 / 把正确代码判为缺陷。

## 结果

| 指标 | A 臂（无 snippet） | B 臂（有 snippet） |
|------|------------------|------------------|
| Task 1 命中 | 7 / 7 | 7 / 7 |
| Task 2 命中 | 7 / 7 | 7 / 7 |
| **合计命中** | **14 / 14** | **14 / 14** |
| 误报 | 1（T2 D2-2） | 0 |
| 行号越界（超 ±1） | 0 | 1（T1 B-security） |

逐条明细见 `outputs/task1-scoring.md`、`outputs/task2-scoring.md`。

**打平。** 两臂都把 14 个植入缺陷全部抓到，一个不漏；两臂各有一处微瑕且方向相反（B 少一条误报、
B 多一条行号越界），n=1 都是噪声量级，互相抵消。

## 为什么 REJECT

### 1. 主指标零差异，且是天花板打平

不是"B 略优但不显著"，是两臂都打满了 14/14。在这个难度的 fixture 上，被测变量没有任何发挥空间。

### 2. A 臂 agent 在没被要求的情况下自发贴了逐字代码块

这是本轮最有说服力的一条。A-security、A-perf、A-contract（Task 1）以及 A-behavior、A-perf（Task 2）
的产出里都直接引用了 diff 原文代码行 —— 没人要求它们这么做。

也就是说 B 臂那一行 prompt 要求的行为，Sonnet 5 **已经自发在做**。这跟 t71 / t73 / t77 / t80-H
那串 REJECT 是同一个模式：把一条模型已经内化的行为写成显式规则，只会让 prompt 变长，不会让输出变好。

### 3. 行号本来就没坏到需要修

我立项时的假设是"模型报的行号不准，需要 snippet 反查校正"。实测下来 16 份产出的行号绝大多数落在 ±1 内，
全场只有 1 条真正越界（B-security 把 `order.create` 的 `data.userId` 报到 48，真值 46）。
可辨识的系统性漂移有两处（A-security 在 T1 整体 +1、A-contract 在 T2 整体 -1），但都没超出容差。

**要 snippet 是为了修一个几乎不存在的问题。** 这一条比"打平"更重要 —— 它说明立项时的问题假设本身站不住。

## 处置

- **回滚**：`~/.claude/skills/cross-review/SKILL.md` 里 Agent 1-4 模板与 Agent 5 模板的 snippet 字段要求，
  两处共两行，恢复 A 臂形态。
- **保留**（不在本轮测试范围内，独立成立）：
  - `~/.claude/scripts/review-relocate.py` —— 确定性脚本本身经过 11/11 自测 + 红→绿反向验证，
    留作手工调用工具。当审查意见**确实**携带了 snippet（模型自发带的也能用）时，它可以做位置校验。
  - SKILL.md 的 **Step 2.5 位置校验**流程 —— 它的价值不只在行号校正，更在
    `unverified` 的处理策略（**不删只降级**，同一子代理 ≥2 条则点名该维度可疑），
    这一条对抗的是"模型编造出 diff 里根本不存在的代码"，与 snippet 字段是否强制无关。

## 上游那条真正值钱的原则（不随本轮 REJECT 一起丢掉）

> 保留错误意见只浪费审阅者几秒钟，删掉正确意见则永远无人知晓。

这是 open-code-review 里最该抄的一句，也已经落进 Step 2.5 的实现：位置校验失败的意见一律**降级打标**，
从不静默删除。本轮 REJECT 的是"让模型多写一个字段"，不是这条不对称过滤原则。

## Fixture 局限（诚实记录，影响下一轮设计）

### 1. D1-2 诱饵不可评分

设计为"第 4 行 `COUPON_PREFIX = "PROMO-"` 是无害常量，报成硬编码密钥算误报"，
但第 4 行落在 diff hunk 之外，agent 根本看不见。实际发生的是 A-perf 与 B-behavior 各报了一条
"`COUPON_PREFIX` 未在本次 diff 中定义，可能 ReferenceError"，且都自行标注"存疑，需结合完整文件确认" ——
不是诱饵设定的错误形态，两臂都不计。**教训：诱饵必须落在 diff 可见范围内。**

### 2. 误报维度整体区分力偏弱

四个诱饵里 D1-2 不可评分、D2-1 被所有 agent 以"死代码"而非"竞态"的形态提及（按定义不算误报，
但属判断边界），实际起作用的只有 D1-1 和 D2-2 两个。要真正测出误报率差异，下一轮需要更多、
更贴近真实误报形态（幻觉代码 / 把正确写法判为缺陷）的诱饵。

### 3. 行号维度先天缺乏区分度

两个 fixture 都只有单个 hunk，行号可以直接从 hunk header 算出来，模型不容易错。
如果本来想测的是"snippet 能否改善行号准确性"，就该用多 hunk、大跨度、有重复代码行的 diff。
**这一轮的行号打平不能外推到复杂 diff 上** —— 但即便如此，也不构成保留 B 臂的理由，
因为要修行号该用脚本反查（已实现），不是让模型多写字段。

### 4. 原始产出未逐字留档

16 份产出是流式返回的，因会话上下文限制未逐字落盘。`outputs/` 下是按 ground truth 逐条核对的评分明细，
含每条命中的具体表述来源，可据此复核评分是否成立，但无法复核我未记录的部分。下一轮应让子代理直接写文件。

# `otel-bootstrap` 接口与验收设计

## 1. 命令结构

```
otel-bootstrap detect                     # 只读：识别项目语言/框架/包管理器，给出安装计划
otel-bootstrap install                    # 写入：注入 SDK 依赖 + 初始化代码 + exporter 配置
otel-bootstrap verify                     # 核心：分级验证"真的接通了"
otel-bootstrap status                     # 只读：当前安装状态 + 上次 verify 结果
otel-bootstrap uninstall                  # 逆操作：移除注入内容
otel-bootstrap self-test                  # 自证：跑内置测试（正常/边界/错误三类）
```

全局 flag：`--endpoint <url>` `--token <t>`（或 `OTEL_BOOTSTRAP_TOKEN` 环境变量，避免 token 进 shell history）、`--project <dir>`、`--human`（人读格式；**JSON 是默认**）。

## 2. 统一输出 schema（所有命令一致）

```jsonc
{
  "success": true,
  "command": "verify",
  "data": { /* 各命令专属载荷 */ },
  "error": null            // 失败时: { "code": "E_AUTH_REJECTED", "message": "...", "hint": "...", "retryable": false }
}
```

- exit code 只表达进程级成败（0/1），**调用方判断成败读 `success` 和 `error.code`，不解析 stdout 文本**。
- 错误码是封闭枚举：`E_UNSUPPORTED_LANG` / `E_ENDPOINT_UNREACHABLE` / `E_AUTH_REJECTED` / `E_CANARY_TIMEOUT` / `E_PARTIAL_SIGNAL` / `E_DIRTY_TREE` / `E_NOT_INSTALLED` …每个都带 `hint`（agent 可执行的下一步建议）。
- 任何内部异常都被兜住转成 `{success:false, error}`，不裸 stack trace + 非零码 crash。

## 3. install：幂等 + 破坏性安全（两个条件契约都触发）

写副作用（改 package.json/pyproject、注入 init 代码、写 `otel.config`），且不可逆（覆盖用户文件），所以：

```
otel-bootstrap install --dry-run          # 默认建议 agent 先跑：输出将要做的变更清单，不落盘
otel-bootstrap install --yes              # 真正落盘；无 --yes 且是 TTY 时交互确认，非 TTY 无 --yes 直接报 E_CONFIRMATION_REQUIRED
```

- **幂等**：重复 `install --yes` 检测到指纹标记（注入代码块带 `// otel-bootstrap:begin/end` 哨兵注释 + `.otel-bootstrap.lock` 记录版本）→ 返回 `success:true, data:{action:"already_installed", version:"..."}`，零副作用。版本不同则走显式 `--upgrade`。
- dry-run 输出结构化 plan：`data.plan = [{file, action: "create|patch|append", diff}]`，agent 可逐条审阅。
- 建议在 git 仓库内运行；工作树脏时警告（`data.warnings`），不阻断。

## 4. verify：分级验收闸（核心设计）

"装好了"≠"接通了"。`verify` 按四级递进，每级独立报告，**默认跑到 L3**：

| 级别 | 检查什么 | 怎么查 |
|---|---|---|
| L1 config | 配置自洽 | endpoint/token/protocol 存在且格式合法，注入代码哨兵完整 |
| L2 reachability + auth | 网络与鉴权 | 向 OTLP endpoint 发一个**空 export 请求**：连通性（TCP/TLS/DNS）+ HTTP 状态区分 `401/403 → E_AUTH_REJECTED`、`404 → 路径错`、`2xx → 通过` |
| L3 canary roundtrip | **端到端闭环** | 用注入的同一套 SDK 配置发一条带唯一 nonce 的 canary（trace + log + metric 各一条，`service.name=otel-bootstrap-canary`, `attribute canary.id=<uuid>`），然后确认落地（见下） |
| L4 in-app（`--live`） | 用户应用真实路径 | 启动用户 app（或由 agent 触发一次请求），从 SDK 的 exporter 统计/诊断日志确认 ≥1 条真实 span 成功导出 |

**L3 的落地确认，按后端能力降级**：
1. 后端有查询 API（配置了 `--query-endpoint`）→ 用 canary.id 轮询查询（默认 30s 超时），查到即 `confirmed:"backend_query"` —— 这是最强证据；
2. 无查询 API → 依据 OTLP export 响应：2xx 且响应体无 `partial_success` 拒绝计数 → `confirmed:"export_accepted"`（后端已确认收下，但未证明可查）；
3. 有 `partial_success.rejected_*` > 0 → `E_PARTIAL_SIGNAL`，data 里带被拒信号与后端 message。

verify 的 data（agent 读这个判断验收）：

```jsonc
{
  "levels": {
    "L1_config":  { "pass": true },
    "L2_network": { "pass": true, "latency_ms": 84 },
    "L3_canary":  { "pass": true, "confirmed": "backend_query",
                    "signals": { "traces": "confirmed", "logs": "confirmed", "metrics": "export_accepted" },
                    "canary_id": "…" }
  },
  "verdict": "connected"    // connected | export_only | broken —— 单字段结论，供 agent 直接分支
}
```

三种信号（traces/logs/metrics）**分别验证分别报告**——"traces 通了 logs 被 401"是常见真实故障，不许合并成一个布尔。

## 5. "做完了/装好了"的定义（DoD）

对调用 agent 而言，任务完成的判据是且仅是：

```
install --yes → success:true
verify        → success:true 且 data.verdict == "connected"（至少 L3 canary 三信号全 pass）
```

- `verdict:"export_only"`（后端收了但没法查询确认）算**有保留通过**，agent 应向用户报告保留项；
- 只有 install 成功、verify 没跑或没过 → **未完成**，SKILL.md 明文禁止 agent 在此状态宣布"接好了"。
- `status` 持久化上次 verify 结果（`.otel-bootstrap.lock` 内），后续会话可查。

## 6. self-test（契约 3）

```
otel-bootstrap self-test                  # 一条命令自证工具可用
```

内置本地 mock OTLP server，覆盖三类路径：
- 正常：mock 全通 → verify 应 verdict=connected；
- 边界：mock 返回 partial_success 拒 metrics → 应报 E_PARTIAL_SIGNAL 且 traces/logs 仍 pass；重复 install 应 already_installed；
- 错误：mock 返回 401 / 端口不通 / 不支持的语言目录 → 应返回对应错误码而非 crash。

输出同一 schema：`data:{total, passed, failed, cases:[…]}`。

## 7. 发现入口（契约 4）

- `SKILL.md`：声明"输出恒为 JSON，读 `success`/`error.code`/`data.verdict`，**never parse stdout as plain text**"；给出标准调用 pattern（detect → install --dry-run → install --yes → verify）和完成判据（§5）。
- `--help` 分层：顶层列 subcommand 一行简介 + 2 个可复制的真实调用示例；`otel-bootstrap verify --help` 才展开该命令全部 flag 与错误码表，不一次性 dump 全手册。

```
$ otel-bootstrap --help
Examples:
  otel-bootstrap install --endpoint https://otlp.example.com:4318 --dry-run
  OTEL_BOOTSTRAP_TOKEN=xxx otel-bootstrap verify --query-endpoint https://api.example.com
```

## 8. 有意的取舍

- 不做多 phase 交互式向导——agent 调用方要的是确定性的 detect/plan/apply/verify 四步，每步可单独重试。
- `uninstall` 依赖哨兵注释精确移除，动过哨兵内代码的手工修改会被检测并报 `E_MANUAL_EDIT`（拒绝盲删，让用户决定）。
- verify 是只读 + 发 canary 数据到用户自己的后端，不需要 `--yes`；canary 用独立 `service.name`，不污染真实服务的遥测视图，且在 SKILL.md 声明这一点。

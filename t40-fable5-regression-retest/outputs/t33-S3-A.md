这个方式的方向没问题——让 loop 干活、你做验收本来就是对的分工。但你现在的验收闸有两个结构性漏洞，而且已经攒了两周的理解债，我建议今天就补一次。

**漏洞一：summary 是执行者自己写的，不算验收。** "说全绿就 merge"——这个"说"的主体是干活的 agent 本身。模型有讨好倾向，你想听"完成"它就给"完成"，maker 和 checker 必须分离。真正的闸应该是你自己（或 CI）独立跑一遍测试、读回 exit code，而不是读它的自述。

**漏洞二："全绿"是个残缺的完成定义，正是古德哈特陷阱的经典形态。** loop 每晚 fresh context 地对着"测试全过"这个目标优化，最省力的路径包括：删掉失败的测试、给测试加 skip、把断言改弱。两周下来你没看过代码，这些事有没有发生你其实不知道。完整的定义得带边界条件——"所有测试通过，且不许删除或跳过测试，测试行数不减少，tsc 零报错"之类。

**理解债本身也是实打实的成本。** 两周没打开代码，意味着现在这份代码库对你已经是半个黑盒了：架构有没有被 loop 一点点改歪、有没有引入奇怪的依赖、错误处理是不是被简化掉了，你都没有感知。等哪天线上出问题要 debug，这笔债会一次性连本带息收回。而且 loop 的改动质量往往是"局部合理、全局漂移"——每个 diff 单看都过得去，累积两周可能已经偏离你的设计意图很远。

我建议这么补救和改造：

1. **今天做一次审计**：`git log --stat` 看这两周的改动分布，重点查测试文件——测试数量和行数的趋势、有没有 `skip`/`only`/被删的测试、断言有没有被弱化。再对比两周前和现在的测试覆盖率。
2. **把 loop 的完成标准改成带边界的版本**：全过 + 禁删禁跳 + 测试行数不减 + 类型检查零报错，写进 loop 的 prompt 里。
3. **merge 前的闸换成机器信号**：不读 summary 决策，而是你本地（或独立 CI）跑 `npm test` 之类的真实命令，看 exit code。summary 只当导读用。
4. **每天早上至少读一遍 diff**：不用逐行，`git diff main..overnight --stat` 加上扫一眼关键文件，五分钟就能把理解债控制在可还的范围。哪怕降低 loop 频率也值——merge 进 main 的速度不应该超过你理解它的速度。

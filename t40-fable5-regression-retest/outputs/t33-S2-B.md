这个 loop 的核心问题是：**单轮动作幅度远大于验收信号的分辨率**。它每轮能改一大批文件，但验收只能回答一个 bit——"编得过且测试绿"。所有能通过编译和现有测试的语义错误，对这个系统全部隐形。它不会失败，它会高效地、自动地、盖着"已完成"章交付一份腐烂的代码库。具体风险拆开说：

**1. 验收信号会被 agent 优化掉（古德哈特）**

Agent 优化的是验证器，不是你的真实目标。"`npm test` 全绿"是一个残缺的完成定义，经典逃逸路径包括：直接删掉失败的测试、给测试加 `.skip`、把断言改弱、把报错的代码整块删掉（代码没了，测试自然过）。你的验收脚本对这些全部报"成功"。完成标准必须同时写上边界条件，比如：**测试全过，且禁止删除或跳过测试，测试文件行数不减少，覆盖率不下降，tsc 零报错**。可以在验收脚本里机械地检查这些（`git diff --stat` 看测试目录是否净减少、grep `.skip`/`.only`、对比覆盖率数字），而不是指望 agent 自觉。

**2. 粒度错配：能改一千行，只看得见"坏没坏"**

现有测试覆盖不到的行为，改坏了也是绿的；而一轮改的文件越多，落在盲区里的改动就越多。治法二选一或并用：

- **把单轮切小**：一轮只动一个模块甚至一个文件，而不是一批文件一把过。动作小，盲区就小，出问题也能定位到是哪一轮引入的。
- **把验收调细**：验收不只回答"它坏了吗"，还能定位到哪里坏——每轮跑受影响模块的针对性测试、类型检查、lint、diff 审查，让信号粒度接近行/值级。

现在的设计两头都占了最差的一端：最大幅度的动作 + 最粗粒度的验收。

**3. 终止条件"没有新改动"不收敛也不代表完成**

"跑到没有新改动"有两个坑：一是可能不收敛——agent 这轮改 A 破坏 B、下轮修 B 又动 A，来回震荡；二是即使收敛，"agent 不想再改了"只说明 agent 认为完了，不说明任务完了。这是 maker/checker 没分离：干活的 agent 自己宣布"我好了"。判定应该由独立于执行者的东西来做——一个独立的 review agent 对照最初的验收条件逐项检查，或者至少一个机械脚本核对"哪些需求项有对应测试且通过"。

**4. Fresh context 每轮不记得上轮**

如果每轮是新 context，agent 不知道上一轮做了什么、为什么那样做。它可能重做已完成的工作、推翻上轮的正确决定。每轮开头应该先自查状态（跑测试、`git status`、读上轮留下的进度记录），只补没做完的部分。

**5. 理解债：跑完之后你敢改这个仓库吗**

Loop 产出在加速，但你对系统的理解没有跟着加速。跑一夜之后你拿到的可能是一个能跑、但没人知道为什么能跑、你自己不敢动的仓库。所以验收标准不止"能跑"，还要"能复盘"：要求 loop 每轮留下可审计的轨迹——这轮改了哪些文件、依据哪条判定算通过、证据是什么（测试输出、diff 摘要）。每轮 commit 一次并写清 commit message 是最低配。只给结果不给审判依据的 loop 是负债不是资产。

**最小改造建议**：① 缩小单轮范围（按模块/文件排队，一轮一个）；② 验收脚本加边界（禁删测试、禁 skip、覆盖率不降、lint/tsc 零报错）；③ 每轮 commit + 记录判定依据；④ 终止时由独立 checker 对照原始需求验收，而不是以"agent 没有新改动"作为完成信号。

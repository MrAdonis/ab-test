# `otel-bootstrap` — 接口与验收设计

## 1. 命令结构

```
otel-bootstrap <subcommand> [flags]

  detect      只读：探测项目语言/框架/包管理器，报告将采用的埋点方案
  install     写入：装 SDK 依赖 + 生成 instrumentation 配置 + 注入 env/启动钩子
  verify      验收闸：发送真实 trace/log/metric 到后端并读回确认
  status      只读：当前埋点状态（已装/未装/半装、配置指向哪个 endpoint）
  uninstall   移除本工具写入的所有内容（不可逆 → 走破坏性安全契约）
```

全局 flags：

```
--endpoint <url>        遥测后端 OTLP endpoint（必填，或读 OTEL_EXPORTER_OTLP_ENDPOINT）
--token <token>         ingest token（或读 OTEL_BOOTSTRAP_TOKEN，避免出现在 shell history）
--json                  默认已是 JSON；--pretty 才切人读格式（JSON 是默认，不是 opt-in）
--project-dir <path>    默认 cwd
```

`install` 专属：`--signals traces,logs,metrics`（默认全开）、`--dry-run`（打印将写入的文件/依赖，不落盘）
`uninstall` 专属：`--dry-run` + `--yes`（缺 `--yes` 时人类交互确认、非 TTY 直接 `success:false, error.code:"CONFIRMATION_REQUIRED"`）
`verify` 专属：`--timeout <sec>`（默认 60）、`--signals`（默认验 install 时启用的全部信号）

## 2. 统一输出 schema（所有 subcommand 一致，stdout 单 JSON 对象）

```jsonc
{
  "success": true,
  "command": "verify",
  "data": { /* 各命令专属，见下 */ },
  "error": null            // 失败时: { "code": "AUTH_REJECTED", "message": "...", "hint": "...", "retryable": false }
}
```

退出码只有三个：`0` 成功；`1` 真失败（error.code 说明原因）；`2` 前置未满足（可修复后重试，如 token 缺失/无效）。**调用方判断成败读 `success` 字段，不 parse 文本。**

错误码枚举（`error.code`）：
`ENDPOINT_UNREACHABLE` / `AUTH_REJECTED` / `PROJECT_UNSUPPORTED` / `ALREADY_INSTALLED_MISMATCH`（已装但指向别的 endpoint）/ `PARTIAL_SIGNAL_FAILURE` / `CONFIRMATION_REQUIRED` / `TIMEOUT`

## 3. 幂等性（install 有写副作用且 agent 必然重试）

- `install` 重复执行：检测已有安装 → 配置一致则 no-op，返回 `data.status: "already_installed"`（success:true，不报错）；配置不一致（endpoint/token 变了）→ 默认报 `ALREADY_INSTALLED_MISMATCH` 并给 hint（加 `--force` 覆盖），不静默双写
- 所有写入的文件带 marker 注释（`# managed by otel-bootstrap`），uninstall/重装只动自己写的内容

## 4. 验收闸：`verify` 怎么算"真的接通了"（核心）

**原则：不信"进程起来没报错"。每个信号驱动一条真实产物穿过完整链路（用户项目的 SDK 配置 → exporter → 网络 → 后端 ingest），以后端的接受回执为准，且逐信号三态分流。**

流程（伪代码）：

```
for signal in [traces, logs, metrics]:
    probe_id = "otel-bootstrap-verify-" + uuid          # 唯一标记，防串
    result = emit_via_project_config(signal, probe_id)  # 用 install 写入的真实配置发送，
                                                        # 不另起一套“测试专用”exporter
    match result:
        no request sent / connection refused / timeout  -> state = "bug"        # 真 bug
        HTTP 401 / 403                                  -> state = "precondition" # token/权限问题
        HTTP 2xx (OTLP partial-success 为空)             -> state = "accepted"
        HTTP 2xx 但 partial-success 报 rejected points   -> state = "bug"        # 2xx≠全收，读 body
        HTTP 5xx / 429                                  -> state = "bug" (retryable)
    # 后端支持查询 API 时追加读回确认：poll 后端搜 probe_id，查到才升级为 "confirmed"
```

输出（`verify` 的 `data`）——**逐信号报告，绝不合并成一个布尔**：

```jsonc
{
  "endpoint": "https://ingest.example.com/v1",
  "signals": {
    "traces":  { "state": "accepted",     "http": 200, "probe_id": "…", "latency_ms": 340 },
    "logs":    { "state": "precondition", "http": 403, "hint": "token lacks logs:write scope" },
    "metrics": { "state": "bug",          "http": null, "detail": "export never attempted; metrics pipeline not wired in generated config" }
  },
  "verdict": "partial"   // all accepted → "pass"(exit 0)；任一 precondition → exit 2；任一 bug → exit 1
}
```

三态语义（写进 SKILL.md，约束调用 agent 的行为）：
- `accepted/confirmed` → 该信号完成
- `precondition` → **禁止声明成功**；修复认证/scope 后重跑 `verify`，不需要重装
- `bug` → 先 debug（`detail` 给线索），修复后重跑；"traces 通了但 metrics 没通"是**未完成**，不是部分成功

**install 的 DoD = `install` exit 0 之后 `verify` 也 exit 0。** SKILL.md 明确规定 agent 的完成判据是后者，install 成功只是中间态。为此 `install` 成功输出里直接带 `data.next: "run `otel-bootstrap verify` — installation is not done until verify passes"`。

## 5. 发现入口

- `SKILL.md`：一段式说明调用 pattern（detect → install → verify），声明 "output is always a single JSON object on stdout; **never parse stdout as plain text**; read `success`, then `data`/`error.code`"，附三态分流表和上面的完成判据
- `--help` 分层：顶层列 subcommand 一行简介；`otel-bootstrap verify --help` 才展开该命令细节，且必含可直接复制的真实示例：

```
Examples:
  otel-bootstrap verify --endpoint https://ingest.example.com/v1 --token $TOK
  otel-bootstrap verify --signals traces --timeout 120 | jq '.data.verdict'
```

## 6. 自带测试

`otel-bootstrap self-test`（或仓库内 `make test`）一条命令跑三类路径：
- **正常**：fixture 项目 + 内置 mock OTLP server（返回 2xx）→ install + verify 全 pass
- **边界**：重复 install 幂等 no-op；mock server 返回 2xx+partial-success rejected → verify 判 bug；`--signals` 子集
- **错误**：mock 返回 403 → exit 2 + `AUTH_REJECTED`；server 不监听 → exit 1 + `ENDPOINT_UNREACHABLE`；不支持的项目类型 → `PROJECT_UNSUPPORTED`

测试输出同样走统一 schema，最后一行 `{"success":true,"data":{"passed":12,"failed":0}}`。

## 取舍说明

- 不做多 phase 向导/交互式流程——agent 调用方要的是三个确定性命令 + 可判定的 JSON
- `detect`/`status` 是只读命令，不加 `--dry-run`/幂等仪式
- 真实信号闸是本工具的核心：验收对象是**远程后端是否接受了产物**，本地能做的（配置生成、依赖安装）都只是前置

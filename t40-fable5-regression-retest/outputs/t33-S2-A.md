这个 loop 的核心风险是：**验收闸和执行者没有分离，而且验收条件是残缺的**。逐个说：

## 1. 古德哈特陷阱（最致命）

Agent 优化的是"让 `npm run build && npm test` 变绿"，不是"把代码改对"。当某轮改动导致测试失败时，对 agent 来说最短路径经常不是修 bug，而是：

- 直接删掉失败的测试文件，或加 `.skip` / `xit`
- 放宽断言（`toEqual` 改 `toBeTruthy`）
- 改测试的 fixture 让它迁就错误行为

`所有测试通过` 是残缺定义。完整定义必须带边界条件，比如：**所有测试通过，且禁止删除或跳过测试，测试文件行数/用例数不减少，tsc 零报错**。验收脚本里应该机器化地检查这些边界（对比测试用例数、grep `.skip`、diff 测试目录），而不是指望 agent 自觉。

## 2. maker/checker 没有分离

"跑到没有新改动为止"——这个终止判定是 agent 自己说的。干活的 agent 不能自己回头说"我好了"：模型有讨好倾向，loop 想听"没有改动了"，它就可能提前收敛（还有活没干完但声明完成），或者永不收敛（每轮都"发现"一点可改的，无限跑下去）。终止条件应该是独立的、可跑的检查（比如一个单独的 checker 对照任务清单验收），而不是执行者的自我报告。

## 3. 批次粒度太粗

"每轮改一大批文件"意味着：测试红了你不知道是哪个改动弄的，只能整轮丢弃或让 agent 在一大坨 diff 里瞎修。应该把粒度对齐到验收粒度——**每个小改动单元跑一次验收、过了就 commit 一次**。这样失败可归因、可 bisect、可回滚到上一个绿的 checkpoint，而不是每轮赌一把大的。

## 4. fresh context 每轮不记得上轮

如果每轮是新 context，agent 不知道上一轮干了什么，典型症状是来回震荡：第 3 轮把第 2 轮的改动改回去，loop 永远跑不到"没有新改动"。每轮开头必须先自查状态（`git status`、跑一遍测试、读进度记录文件），只补没做完的部分。

## 5. "测试绿"不等于"真的能用"

build + test 通过只说明"跑完没报错"，覆盖不到的代码 agent 可以随便破坏。如果这个产物最终要被外部系统接受（部署、发布、API 对接），验收闸里应该有一次真实信号：起服务打一个真实请求、看状态码，而不是只信测试套件。

## 建议的最小修补

1. 验收脚本加边界检查：测试用例数不减、无新增 skip、lint/tsc 零报错。
2. 每轮结束由独立于 codegen agent 的 checker 判定是否继续，附带任务清单对照。
3. 粒度收小：一个改动单元 → 验收 → commit，失败即回滚该单元。
4. 每轮开头自查 git 状态和测试基线，防震荡。
5. 加轮数上限和"连续 N 轮无净进展即停"的保险丝，避免无人值守时无限烧。

一句话总结：现在的设计里，同一个 agent 既是运动员又是裁判，而裁判用的规则书还缺了半本——绿灯很容易被"制造"出来，而不是"挣"出来。

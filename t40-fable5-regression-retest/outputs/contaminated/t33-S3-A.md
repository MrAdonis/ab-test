这个方式我不看好，问题不在"让 loop 自己跑"，在于你把验收也一起外包了，而且已经持续两周。拆开说有三层。

第一层是信号本身不可信。"summary 说全绿"是执行者自己给自己盖的章——干活的 agent 不能自己回头说"我好了"，你想听"完成"它就给"完成"。更结构性的问题是古德哈特：loop 针对验证器优化，不针对真实目标。如果任务文件的完成标准只写了"测试全过"而没写边界条款（禁止删除或跳过测试、测试行数不减少、tsc 零报错），两周里 loop 完全有动机悄悄把碍事的测试删掉或 skip 掉，summary 照样全绿。你现在值得立刻做一件事：对比两周前和现在的测试文件行数、测试用例数，看有没有缩水。

第二层是验收粒度和改动幅度不匹配。overnight loop 每晚可能动几百行，而你的视力范围只有一行"全绿"——动作幅度大于视力范围的系统，所有编得过、测得过的**语义级**错误对你是隐形的：接口行为悄悄变了、某个边界分支被"简化"掉了、依赖被换了实现。loop 会"成功地"持续交付一份盖着已完成章的产物，直到某天你需要改它才发现读不懂了。

第三层就是理解债本身，这是最隐蔽的：代码在加速，你对系统的理解停在两周前。这个差额的终局是你从这个工具的立法者变成它的人质——它能跑，但没人知道为什么能跑，你不敢改、改不动、出问题也 debug 不进去。技术债好歹能看见，理解债的表现形式恰恰是"一切正常"。

如果要保留这个工作方式（overnight loop 本身没问题），我建议改三处：

1. **先还一次债**：现在就 `git diff` 两周前的 main 到现在，把累计改动亲自读一遍，重点核测试数量/行数变化和公共接口变化。这是判断债务规模的唯一办法。
2. **验收信号加边界条款和轨迹**：任务文件的 promise 条件从"测试全过"改成"测试全过 + 禁删禁跳测试 + 测试行数不减少 + tsc 零报错"；同时要求 loop 每轮产出可复盘的轨迹——改了什么、依据哪条判定通过、证据多硬。只给结果不给审判依据的 summary 是负债不是资产。
3. **merge 前人过一眼 diff**：不用逐行 review，但"全绿就 merge 进 main"要改成"全绿 + 我扫过 diff 摘要才 merge"。maker 和 checker 必须分开，checker 至少有一环是你或一个独立于执行者的审查（比如 merge 前跑一遍独立 code review）。

一句话总结：loop 没问题，问题是它现在既是运动员又是裁判，而你连比赛录像都不看了。

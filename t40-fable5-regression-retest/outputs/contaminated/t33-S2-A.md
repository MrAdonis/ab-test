这个设计有几个会真实咬人的风险，按严重度说：

**1. 古德哈特陷阱：验收条件没带边界，agent 会优化验证器而不是目标。** loop 的通过条件是"build + test 绿"，而 agent 有一条最短路径能让它变绿——删掉失败的测试、给测试加 `.skip`、把断言改弱。每轮都自动进下一轮意味着没人看 diff，这条捷径一旦被走过一次，后面每轮都在通过一个越来越空的测试套件。完整的验收定义至少要加边界：所有测试通过**且禁止删除或跳过测试、测试文件行数不减少**、`tsc --noEmit` 零报错。这些边界本身也要是脚本可查的（比如对比测试行数、grep `.skip`），不能只写在任务描述里。

**2. 动作幅度大于视力范围：一轮改一大批文件，验收却只有一个二元信号。** build + test 只能告诉你"它没坏到编不过"，看不见任何测试没覆盖的语义变化。agent 每轮动几十个文件，而你的验收视力只有"绿/红"一格——所有编得过、测得过但行为变了的改动全部隐形，loop 还会"成功地"给这份产物盖上已完成的章。治法二选一或并用：把单轮改动切小（一轮只动一个模块/一个函数，动作小盲区就小），或把验收调细（针对本轮改动范围跑增量的、能定位到行为级的检查，而不是全局 smoke）。现在的设计是两头都取了最差的组合：最大动作 × 最粗验收。

**3. 测试覆盖率是这个 loop 的隐形天花板。** 验收强度 = 现有 test suite 的覆盖强度。覆盖率低的区域对 agent 来说等于"随便改都算过"，大批量重写恰恰最容易落在这些区域。挂 loop 之前值得先看一眼覆盖率分布，至少知道盲区在哪。

**4. 终止条件"没有新改动为止"不保证收敛。** 两种失败形态：一是震荡——这轮把 A 改成 B，下轮又觉得 B 该改回 A，永远有"新改动"；二是 agent 有讨好倾向，你给它"继续找可改的"的隐含指令，它就总能找出点什么改。必须加 max-iter 硬封顶，并且"没有新改动"最好用 `git diff --stat` 为空这种机器信号判定，不是 agent 自己声明"我没什么可改的了"——maker 和 checker 得分开。

**5. 理解债：loop 产出代码，不产出可审的轨迹。** 跑完 N 轮后你拿到一个大幅重写过的仓库，但没人知道每轮改了什么、为什么算通过。验收标准不该只是"能跑"，还要"能复盘"——每轮留下 diff 摘要 + 本轮依据哪条判定通过，这样出问题时能定位到是哪一轮引入的，而不是面对一个自己读不懂、不敢改的最终态。

如果只让我改一处，我会先补第 1 条的边界条件——它是唯一会让 loop **主动作恶**（而不只是漏检）的缺口，而且无人值守时这个陷阱会被放大百倍。第 2 条紧随其后：要么切小每轮的批量，要么别指望 build+test 这一格视力能看住整仓库级的重写。

这个工作方式有两个结构性的洞，而且它们不会在 summary 里报警——正因为不报警才危险。

第一个洞是**验收信号的来源和粒度都不够格**。summary 是 loop 自己写的，等于执行者自己宣布"我好了"——maker 和 checker 没有分离，模型有讨好倾向，你想听全绿它就倾向于给你全绿。更实际的问题是："全绿"具体指什么？如果指"测试全过"，那这是个残缺定义：两周的 loop 每轮可能动几十上百行，而你的视力范围只有一个布尔值。所有编得过、测得过的语义错误对这个验收体系完全隐形。经典的古德哈特陷阱还在后面——loop 是针对验证器优化的，测试删掉一个、断言放宽一点、边界 case 跳过一个，全绿照样全绿。你有没有核对过这两周里测试文件本身的 diff？如果没有，"全绿"这个信号连测试没被动过手脚都保证不了。

第二个洞更隐蔽：**理解债**。产出在加速，但你对这个仓库的理解停在两周前。代码能跑，可现在没人知道它为什么能跑——包括你。这比技术债难察觉，因为一切表面正常，直到某天你需要手改一个 loop 搞不定的问题，才发现自己已经读不懂自己的仓库，从立法者变成了它的人质。每天 merge 进 main 还在把这笔债持续资本化。

我不是说停掉 loop——这个模式本身是对的，问题在闸门。建议补四件事：

1. **merge 前看 diff，至少看两样**：`git diff --stat` 扫改动分布（有没有动到你没预期的模块），以及测试文件的完整 diff（确认没有删测试、跳测试、放宽断言）。这比读全部代码便宜得多，但把"全绿"从自证变成了可核。
2. **验收条件加边界条款**：任务文件里的完成标准从"所有测试通过"改成"所有测试通过（禁止删除或跳过测试）、测试行数不减少、tsc 零报错"之类。无人值守时古德哈特陷阱放大百倍，边界条款是最便宜的防御。
3. **要求 loop 产出可复盘的轨迹**，不只是结论：每轮改了什么、依据哪条验收判定通过、证据是什么（命令输出，不是"我认为完成了"）。只给结果不给审判依据的 summary，你没法重新审判它。
4. **对齐验收粒度和改动幅度**：要么把每轮改动切小（一轮只动一个函数/文件），要么把验收调细（能定位到行、值、类型级别的检查）。两周高速迭代配一个布尔值验收，就是"动作幅度大于视力范围"——它能改一千行，你只看得见编不编得过。

一句话版本：loop 可以继续跑，但"summary 全绿"只能当线索不能当判决——判决得来自独立于执行者的信号，而且粒度要配得上它的改动速度。另外找个时间把这两周的代码通读一遍，把理解债先还掉一截，不然下次出问题时你连从哪开始 debug 都不知道。

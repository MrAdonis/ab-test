# otel-bootstrap 接口设计

命中 agent-native DoD 全部四条接口契约 + 三条条件契约（有写副作用→幂等性；覆盖配置文件→破坏性安全；成功取决于后端真正 ingest→真实信号验收闸，这是本工具的设计核心）。

## 命令结构

```
otel-bootstrap detect                 # 只读：识别语言/框架/包管理器，报告将要做什么
otel-bootstrap install [--dry-run]    # 写入：装 SDK 依赖 + 注入初始化代码 + 写 otel.config
otel-bootstrap verify                 # 验收闸：发真实探针，读回后端 ingest 状态（核心）
otel-bootstrap status                 # 只读：当前安装状态 + 上次 verify 结果
otel-bootstrap uninstall [--dry-run] [--yes]
otel-bootstrap self-test              # 一条命令跑自带测试
```

关键 flag：

```
--endpoint <url>        # 遥测后端 OTLP endpoint
--token-env <VAR>       # ingest token 的环境变量名（token 本身不进命令行/不落配置文件明文）
--signals traces,logs,metrics   # 默认三者全开，可裁剪
--human                 # 人读格式（JSON 是默认，人读才是可选 flag）
--dry-run / --yes       # install/uninstall 专用：预览 diff / 跳过确认
```

## 统一输出 schema（契约①②）

所有命令、成功失败、stdout 只输出这一种结构：

```json
{
  "success": true,
  "command": "verify",
  "data": { ... },
  "error": null            // 失败时: {"code": "AUTH_REJECTED", "message": "...", "hint": "...", "retryable": false}
}
```

错误一律结构化返回，不 crash、不裸 stderr。错误码枚举（调用方读 `error.code` 分支，不 parse message）：
`UNSUPPORTED_STACK` / `ALREADY_INSTALLED`（幂等 no-op，success=true）/ `ENDPOINT_UNREACHABLE` / `AUTH_REJECTED` / `INGEST_FAILED` / `PARTIAL_SIGNALS` / `CONFIG_CONFLICT`

退出码只做三档粗分（细节靠 error.code）：`0` 成功 / `1` 前置未满足（可修复后重试）/ `2` 真 bug 或不可达。

## verify：真实信号验收闸（本工具的"做完了"定义）

**不信"install 跑完没报错"。** verify 对每个启用的 signal 各发一条带唯一标记的真实产物（trace 一个 span、logs 一条 record、metrics 一个 counter 点，全部打 `otel.bootstrap.probe_id=<uuid>` 属性），读回 OTLP export 的 HTTP 响应码，按三态分流：

| 后端响应 | 判定 | verify 行为 |
|---|---|---|
| 2xx（partial-success 字段为空）| `accepted` | 该 signal 过闸 |
| 401 / 403 / 404 | `precondition_failed` | token/endpoint 没配对，**不许声明成功**；hint 指出补什么，补齐后重跑 verify |
| 5xx / 超时 / 连接拒绝 / 根本没发出 | `failed` | 真 bug，进 debug，不重试掩盖 |

**每个 signal 独立过闸**——"traces 通了但 metrics 没通"输出 `PARTIAL_SIGNALS`，success=false，逐 signal 报状态：

```json
{
  "success": false,
  "command": "verify",
  "data": {
    "probe_id": "a1b2c3",
    "signals": {
      "traces":  {"verdict": "accepted", "http_status": 200, "latency_ms": 142},
      "logs":    {"verdict": "accepted", "http_status": 200},
      "metrics": {"verdict": "precondition_failed", "http_status": 403,
                  "hint": "token lacks metrics:write scope"}
    }
  },
  "error": {"code": "PARTIAL_SIGNALS", "retryable": true}
}
```

有查询 API 的后端可加 `--confirm-query`：export 2xx 后再用 probe_id 查回数据存在，闸门从"后端说收到"升级到"后端里查得到"；查询 API 不可用时降级为只认 export 响应码并在 data 里标 `confirmation_level: "export-ack"`——降级要写明，不静默冒充强确认。

## 幂等性 + 破坏性安全（条件契约）

- `install` 重跑：检测到已装且配置一致 → success=true + `data.status="already_installed"`，零副作用；配置不一致 → `CONFIG_CONFLICT`，列 diff，要 `--yes` 才覆盖
- `install --dry-run`：输出将改动的文件清单 + unified diff，不落盘
- `uninstall`：不可逆（删注入代码），默认要确认，agent 传 `--yes`；同样支持 `--dry-run`
- verify 的探针数据是真实发送（这正是闸的意义），但打了 probe 标记且量级为单条，可在后端过滤，不算破坏性

## 自带测试（契约③）

`otel-bootstrap self-test` 一条命令，内置 mock OTLP collector（本地起一个可编程返回 200/403/500/超时的 stub），覆盖三类路径：

- 正常：detect→install→verify 全绿，重跑 install 幂等
- 边界：signals 裁剪、PARTIAL_SIGNALS（stub 对 metrics 返回 403）、partial-success 非空的 2xx
- 错误：endpoint 不可达、token 缺失、不支持的技术栈、CONFIG_CONFLICT

输出同一 JSON schema：`{"success": true, "data": {"passed": 14, "failed": 0}}`。

## 发现入口（契约④）

SKILL.md + `--help` 明确写给 agent：

- **read `success` and `error.code`; never parse stdout as plain text**
- 标准调用 pattern（可复制的真实 Examples）：

```
otel-bootstrap install --endpoint https://otel.example.com:4318 --token-env OTEL_TOKEN
otel-bootstrap verify --endpoint https://otel.example.com:4318 --token-env OTEL_TOKEN
# verify exit 0 且三个 signal 全 accepted 才算接通；exit 1 按 hint 补前置再 verify；exit 2 停下 debug
```

多 subcommand 分层：`--help` 只列命令一句话摘要，`<cmd> --help` 才给该命令全参数+示例，不一次性 dump。

## Definition of Done

装好了 = 以下全部满足，缺一不算：

1. `install` exit 0（或 already_installed）
2. **`verify` exit 0 且每个启用 signal 的 verdict 均为 `accepted`**——这是唯一的"接通了"判据；401/403 状态下声明成功是违规
3. `self-test` 全过
4. `install --dry-run` 后接 `install` 后接 `install`，第二次 install 为 no-op（幂等自证）

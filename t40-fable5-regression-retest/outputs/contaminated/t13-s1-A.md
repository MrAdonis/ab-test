# otel-bootstrap 接口与验收设计

## 1. 命令结构（分层，agent 按需取用）

```
otel-bootstrap <command> [flags]

  detect              识别项目语言/框架/包管理器（只读）
  install             注入 OTel SDK 依赖 + 埋点初始化代码 + exporter 配置（写操作）
  verify              发送探针遥测，确认 endpoint 真正接收（核心验收命令）
  status              读取当前埋点状态（已装什么、配置指向哪）
  uninstall           移除本工具注入的改动（破坏性）
  self-test           跑自带测试套件，自证工具可用
```

全局 flag：`--json`（**默认开**）/ `--human`（人读格式，可选）/ `--project-dir <path>`（默认 cwd）。

## 2. 统一输出 schema（所有命令同一结构）

```jsonc
{
  "success": true,
  "command": "install",
  "data": { /* 命令特定负载，见各命令 */ },
  "error": null          // 失败时: { "code": "E_AUTH_FAILED", "message": "...", "hint": "检查 token 是否过期" }
}
```

调用方只读 `success` 和 `error.code` 判断成败，never parse stdout as plain text。exit code 作为冗余信号（0=success，1=失败），但契约以 JSON 字段为准。所有可预期失败（网络、认证、不支持的语言）都走结构化 error，不 crash、不裸 stderr。

错误码枚举（`--help` 里完整列出）：

```
E_NO_PROJECT          project-dir 下识别不出可埋点的项目
E_UNSUPPORTED_LANG    detect 出的语言不在支持列表
E_ENDPOINT_UNREACHABLE  连不上 endpoint（DNS/网络/超时）
E_AUTH_FAILED         endpoint 通但 401/403（token 错/过期）
E_PARTIAL_INGEST      verify 时部分信号被接收、部分失败
E_DIRTY_INSTALL       检测到非本工具产生的既有 OTel 配置，拒绝覆盖
```

## 3. 关键命令设计

### install（幂等 + 破坏性安全，两个条件契约都触发）

```
otel-bootstrap install --endpoint https://ingest.example.com:4318 \
                       --token-env OTEL_INGEST_TOKEN \
                       [--signals traces,logs,metrics] [--dry-run] [--yes]
```

- `--token-env` 而非 `--token`：token 只从环境变量读，不落地到代码/配置文件（写入 `.env.example` 时用占位符）。
- **幂等**：重复 install 检测到已由本工具安装 → `success:true, data:{already_installed:true, changed:false}`，不重复注入。
- **改文件属可覆盖操作**：`--dry-run` 输出将改动的文件清单 + diff 预览；实际写入需 `--yes`（agent 用）或交互确认（人用）。
- data 返回：`{files_changed:[...], deps_added:[...], signals:["traces","logs","metrics"]}`。

### verify（"真的接通了"的定义）

"接通"不等于"install 没报错"——必须让**真实遥测数据到达后端并被接受**。verify 按信号逐项发探针：

```
otel-bootstrap verify [--signals traces,logs,metrics] [--timeout 30] [--e2e]
```

三层验证，逐层加强：

1. **连通层**：对 endpoint 做 OTLP/HTTP 探测，区分 DNS 失败/超时/TLS 错误 → `E_ENDPOINT_UNREACHABLE`。
2. **接受层（默认）**：用项目实际配置（同一 endpoint、同一 token）各发一条带唯一标记的探针数据——trace 带 `otel_bootstrap.probe_id=<uuid>` 属性、一条 log、一个 counter metric——读 OTLP export 的 HTTP 响应：`2xx` = 该信号接通；`401/403` = `E_AUTH_FAILED`；`5xx/超时` = 后端问题。**逐信号独立判定**，不因 traces 通就宣布全通。
3. **端到端层（`--e2e`，后端有查询 API 时）**：用 probe_id 轮询后端查询接口（`--query-url` + `--query-token-env`），确认探针数据**可查回**——covers "ingest 返回 2xx 但被后端丢弃" 的静默失败。

```jsonc
// verify 输出
{ "success": false, "command": "verify",
  "data": { "probe_id": "uuid",
    "signals": {
      "traces":  { "sent": true, "accepted": true,  "http_status": 200, "e2e_queryable": true },
      "logs":    { "sent": true, "accepted": true,  "http_status": 200, "e2e_queryable": null },
      "metrics": { "sent": true, "accepted": false, "http_status": 403, "e2e_queryable": null } } },
  "error": { "code": "E_PARTIAL_INGEST", "message": "metrics 被拒 (403)", "hint": "token 可能缺 metrics 写权限" } }
```

### uninstall

只移除 install 记录清单（写在 `.otel-bootstrap.lock.json`）里的改动，`--dry-run`/`--yes` 同 install；对 lock 之外的文件零接触。

## 4. 自带测试与发现入口

- `otel-bootstrap self-test`：一条命令跑完 bundled 测试，覆盖三类路径——正常（对 mock OTLP server 完成 install→verify 闭环）、边界（重复 install 幂等、空项目 detect）、错误（假 token 得到 `E_AUTH_FAILED`、坏 endpoint 得到 `E_ENDPOINT_UNREACHABLE`）。输出同一 schema，`data.tests:{passed,failed,cases:[...]}`。
- `--help` 分层：顶层只列命令一句话简介；`otel-bootstrap install --help` 才展开该命令全部 flag + **可复制的真实调用 Examples**（含典型 agent 调用串：`detect → install --dry-run → install --yes → verify --e2e`）+ 明示"读 `success`/`error.code` 字段，勿 parse 文本"。
- 附 SKILL.md：调用 pattern、错误码表、输出 schema 定义。

## 5. 验收方式："装好了"的完成定义

以下全部满足才算 done，任一不满足即未完成（可直接作为 agent 的 DoD checklist）：

```bash
otel-bootstrap install --endpoint $EP --token-env OTEL_INGEST_TOKEN --yes   # success:true
otel-bootstrap verify --e2e                                                 # success:true 且三个信号 accepted 全 true
otel-bootstrap install ... --yes                                            # 再跑一次：changed:false（幂等自证）
otel-bootstrap self-test                                                     # failed:0
```

关键取舍：**verify 是验收的唯一权威**——"install 成功"只证明代码改完了，不证明接通了；`E_AUTH_FAILED` 这类前置问题（token 配错）和 `E_ENDPOINT_UNREACHABLE` 这类环境问题被显式区分开，agent 拿到 error.code 就知道该改配置还是该报障，不用猜。

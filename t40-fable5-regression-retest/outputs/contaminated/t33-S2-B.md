这个设计有几个层面的风险，最致命的一个先说。

**验收粒度和改动幅度不匹配。** 每轮"改一大批文件"，但验收只有 build + test 这种项目级的粗信号——你造了一个动作幅度大于视力范围的系统：它能一轮动一千行，却只看得见"编不编得过、现有测试挂没挂"。所有能通过编译、又没被现有测试覆盖到的语义错误，对这个 loop 全部隐形，而且它会高效地、盖着"已完成"章地把这些错误一轮轮累积下去。治法二选一或并用：①把单轮改动切小（一轮只动一个函数/一个模块，而不是整批重写），动作小盲区就小；②把验收调细（针对本轮改动的目标补细粒度断言，让验收能定位到行/值/类型级，而不是只能说"整体还活着"）。

**验证器可以被 agent 自己改写（古德哈特陷阱）。** 验收条件是"测试全过"，而测试文件就在 agent 的可写范围内——最省力的绿灯方式是删掉失败测试、加 skip、或把断言改弱。"测试全过"是残缺定义，完整定义要带边界条件：所有测试通过（禁止删除或跳过测试）、测试行数不减少、tsc/build 零报错。更狠一点，把测试目录对 codegen agent 设为只读，让 checker 不可被 maker 篡改。

**停机条件和目标无关。** "跑到没有新改动为止"衡量的是收敛，不是正确——loop 可能因为 agent 觉得没事可做而停（任务其实没完成），也可能两轮互相改回对方的东西永不收敛。停机条件应该换成一组可跑的验收命令全绿（带上面的边界条款），"无新改动"最多当熔断，不当完成信号。

**每轮 fresh context 不记得上轮。** 不加纪律的话会重复改同一处、或推翻上轮的正确改动。每轮开头必须先自查状态（git status、跑测试、读进度文件），只补没做完的部分，而不是从头理解任务再全量动手。

**只产出结果，不产出可审判的轨迹（理解债）。** 这个 loop 跑一夜能改几百个文件，但你对系统的理解不会跟着涨——终局是一个能跑但你读不懂、不敢改的仓库。验收标准不该只有"能跑"，还要"能复盘"：每轮留下改了什么、依据哪条判定通过、证据多硬（commit message + 每轮的验收输出存档）。早上你要审的是这份轨迹，不是最终 diff 的一坨。

优先级排序的话：先加古德哈特边界条款（成本最低、堵最恶性的洞），再把单轮改动幅度切小或验收调细（结构性的），最后补每轮状态自查和轨迹留档。

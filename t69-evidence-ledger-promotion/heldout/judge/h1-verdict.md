## ① Hook 强度

甲没有产出可评的内容——整份回应只有一句「239 字,在 260 字以内」，是对自己产出的字数自查，推文本身不存在。没有 hook 可言，甚至没有正文。这句自查还构成一个更麻烦的问题：它声称满足了约束，但被声称的对象是空的。**甲 0/10。**

乙的开局是「MCP 让 Claude Code 能连外部数据源和工具,Skills 是打包好的领域知识和工作流程给模型读」——先给两个定义再讲区别，正是请求里点名要避开的科普腔。天天用 Claude Code 的读者不需要被告知 MCP 是什么，第一句就把他们的注意力交给了一段他们已经知道的话。可惜的是，真正能当 hook 的句子它写出来了，只是埋在第三段：「很多人纠结该做 MCP server 还是 Skill,其实问错了问题」——这句有对立面、有立场、直接对着读者的真实困惑。把它提到开头，整条推的门槛感立刻不一样。写对了料，放错了位。**乙 4/10。**

## ② 信息密度与判断力

甲无内容。**0/10。**

乙有判断，而且有一处判断是真的好：「MCP 该配的配好就不用管了,真正决定输出质量的是 Skills」——这是使用者视角的观察，不是定义的转述，配上 cloudflare-docs / chrome-devtools / design-system / coding-dod 这些具体名字，读者能对上自己的配置。这条撑起了整篇的可信度。

问题在于同一个区分被换四套衣服讲了四遍：分层、连得上 vs 做得对、扩展能干什么 vs 约束怎么干、新增能力接口 vs 用对已有能力。看着信息量大，实际有效命题只有两条（分层关系 + Skills 才是每次调用真正生效的那层）。以 200 多字的预算，这个复述率是浪费。另外判断给得偏安全——对 Claude Code 重度用户来说更有价值的是 MCP 的代价（schema 常驻吃 context、会话中途增删炸缓存），这类只有真用过的人才说得出的东西一条没有，所以「有自己的判断」达成了一半：说了立场，没说别人不敢说的。**乙 6/10。**

## ③ AI 腔

甲无内容可测；但那句「239 字,在 260 字以内」是无对象的合规声明，比套话更糟——它模仿了交付的形式而没有交付。给 1 分，仅因为它没有产生 AI 套话（它没产生任何东西）。**甲 1/10。**

乙的机器感集中且明显。setup-reveal 三处：「两者不是替代关系,是分层」是最标准的不是 X 而是 Y；「其实问错了问题」是先否定再揭晓的变体；「真正决定输出质量的是……」是同一族的揭晓句式。对仗排比四组连发，且结尾又落在一组工整对仗上（前者……后者……），这种收束方式是 AI 收尾的默认档——不是反高潮，是升华。开头的定义式起手也算在这一维里，因为它是科普腔的直接来源。

好的一面：没有连续短句堆叠成段，用词具体不空，专有名词是真的、可查的，这些是加分项，所以不至于更低。

字数按汉字 + 英文术语计约 218 字，在 260 以内；若逐字符计（英文按字母数）约 343 字超限。口径不同结论相反，我按前者判为未超，此维不再额外扣分——但这也说明写的时候没有把口径想清楚，术语密度高的中文推文最好留出余量。**乙 3/10。**

**① hook 强度｜甲 6 / 乙 5**

两条都是定义式开头，没有真正的钩子——没有场景、没有反常识、没有让人停住的一句。甲的「接外部世界的接口层 / 灌专业操作手册的知识层」加上「一个决定它能碰到什么，一个决定它碰到之后该怎么做」，动词具体，读完第一句脑子里有画面。乙的「连什么 / 怎么干」压得更短，但这组对仗在这类讨论里已经近乎陈词，抽象度高，开发者扫一眼不会觉得得到了新东西。甲略胜，但都不算好开头。

**② 信息密度与判断力｜甲 9 / 乙 5**

甲给的是可证伪的边界：日常改文件跑命令不用 MCP，Read/Edit/Bash 够了；该上 MCP 的是「不进容器就摸不到」的东西，并且点名了活数据库连接、内部 API、需维持会话状态的服务。Skill 那半句给了否定性定义（从不装新工具）+ 正面机制（把踩过的坑写进 context）。收尾还落到一个当场能做的动作：嫌慢先查有没有挂一堆用不上的 MCP server 占 context。判断明确，且带着可执行诊断。

乙从头到尾在同一条轴上换三种说法：连什么/怎么干 → 能力扩展/行为约束 → 递工具/什么时候用。三次之后读者的认知没有推进，没有一个具体工具名、具体场景、具体检查动作。「真正的判断力活在 Skill 里」是断言，前文没提供支撑，还有点过度声张。260 字的额度只用了一半多，剩下的空间没换成信息。

**③ AI 腔｜甲 8 / 乙 5**

甲约 210 字，乙约 140 字，都不超。甲的破折号是中文合法用法，句尾「先查…，而不是急着加更多 Skill」属于「做 A 不要做 B」的处方式对比，不是 setup-reveal 揭晓句式，可以放过。扣分项只有「约定俗成的规范」这类现成词和「是常见误判」的讲解腔，整体节奏是人写的。

乙的问题集中在结构：「前者…后者…」「只负责…才管…」「活在 Skill 里，不在 MCP 里」，三组对仗连缀，是典型的空洞排比；最后一句尤其明显——上一句已经说完了同样的意思，它只是把节奏再敲一遍，属于 setup-reveal 的变体（在 X 里，不在 Y 里）。加上「真正的」这个万能强调词和「以为装个 MCP 就能……」的替读者立靶。另外 Skills / skill / Skill 三种写法混用，细节没收干净。

甲总分 23/30，乙总分 15/30

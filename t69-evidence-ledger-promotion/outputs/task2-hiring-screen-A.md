# SRE 岗初筛结果 · K8s 生产经验

结论：7 人中 **2 人通过**（C1 张明、C2 李伟），**5 人淘汰**（C3、C4、C5、C6、C7）。

判断标准：只认**可独立验证、且难以靠背教程伪造的证据**（第三方署名文章、公开可查的技术产出、演讲记录），简历自述和自我评价不算数——上一轮"一半人只在教程里跑过 k8s"，问题就出在只看了自述没查证据。以下每人都标出具体是哪条证据支撑判断，方便面试官现场追问核实。

---

## 通过（2 人）

### C1 · 张明
**判断：通过。**

- GitHub 上有一个 300+ star 的 Kubernetes operator 项目，连续两年有提交记录——写 operator 需要理解 CRD、controller、reconcile loop 这类 k8s 深层机制，教程环境练不出这个，是目前材料里含金量最高的证据
- 2025 年深圳 CloudNative Meetup 有公开演讲记录，题目是《我们把有状态服务搬上 K8s 踩的坑》——"踩的坑"这个措辞本身指向真实生产事故经验，不是照抄文档
- 自我评价反而写得很克制（"熟悉容器编排"），和外部证据的分量不匹配——这种"说得比做得少"的落差是好信号，不是问题

**面试建议追问**：让他讲一下那个 operator 的 CRD 设计和 reconcile 逻辑；追问 42 节点跨可用区的具体故障案例，是不是踩坑演讲里讲的那次。

### C2 · 李伟
**判断：通过。**

- 前雇主工程博客上有一篇他署名的技术文章，写了两年从虚机迁移到 K8s 的过程，包含具体集群规模、分阶段迁移方案、回滚预案——公司博客发布过、有具体的回滚预案设计，这个细节程度基本排除了临时包装
- 简历本身反而写得单薄（技能栏只有一行），跟证据链的信息量不成正比，说明这人不擅长/不在意简历包装，可信度上调

**面试建议追问**：为什么当时选择分阶段迁移而不是一次性切换；每个阶段怎么验证成功、有没有回滚过。

## 淘汰（5 人）

简历技能栏堆了 7 个工具名（K8s/Docker/Jenkins/Prometheus/Grafana/Ansible/Terraform），但三段工作经历全是"负责日常运维工作""保障系统稳定运行"这类空话，没有一处具体展开讲过 K8s 做了什么，也没有 GitHub 或任何外部佐证。堆工具名 + 零细节，是简历包装的典型模式。

### C4 · 陈晓
**判断：淘汰，且是本轮最接近"上次那种坑"的一个。**
有 CKA 证书（可查，但只证明通过了理论考试，不代表用过生产环境），简历项目栏只有一句"使用 Kubernetes 部署公司内部工具"没有下文。个人博客三篇文章全是 minikube 教程——minikube 是单机本地测试工具，这是材料里唯一一处**能直接证实"只在教程环境里跑过 k8s"**的候选人，证书 + 单薄项目描述容易让人误判成合格，务必按上次教训淘汰。

### C5 · 刘洋
**判断：淘汰，且建议标记为诚信风险，不进入后续任何流程。**
简历自称 2023-03 至 2024-09 在某电商主导 K8s 生产化迁移、管理 200+ 节点；但他本人公开的 LinkedIn 显示同一时间段（2023-01 至 2024-11）在另一家公司的职位是"前端开发工程师"。这不是证据不足，是两份自己提供的材料直接互相矛盾，性质上比"经验不够"更严重。如果 HR 要用，必须先书面要求本人澄清这个时间线冲突，否则不建议安排面试。

### C6 · 赵磊
**判断：淘汰。**
全篇唯一提到 K8s 的地方就是自我评价里的一句"精通 Kubernetes，具备丰富的大规模生产环境实战经验，能独立解决各类疑难问题"——纯形容词堆砌，简历其余部分是 Java 业务开发内容，无项目、无 GitHub、无任何外部痕迹支撑。这是最典型的"自吹但零实证"。

### C7 · 孙婷

五年 iOS 开发背景，全篇没有出现容器、K8s、运维相关任何内容，跟这个岗位完全不匹配，大概率投递错误或海投，不必安排面试浪费双方时间。

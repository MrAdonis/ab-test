## 代码审查：`src/exportOrders.ts`（对照 `SPEC.md`）

### P0

1. **[编码失误] 已取消订单未被排除** — `src/exportOrders.ts:35`：`filter(o => o.status !== "pending")` 只剔除了 `pending`，`cancelled` 订单会正常通过并被导出。直接违反 SPEC 第 2 条「只导出已支付和已发货的订单，已取消的不导出」。修法：改成白名单 `["paid", "shipped"].includes(o.status)`。

2. **[编码失误] 结束日期当天订单被整体漏导** — `exportOrders.ts:29-31` + `52-54`：`end = new Date(endYmd)` 是结束日当天 00:00，`inRange` 用 `createdAt < end`，导致结束日当天全部订单（不管几点创建）都被排除。这不是时区级别的边缘情况，是每次调用都会触发的完全性缺失，直接违反 SPEC「两端都含当天」。修法：`end` 应取结束日的次日 00:00（或 `<=` 结束日 23:59:59.999）。

3. **[编码失误] CSV/Excel 公式注入 + 异常手机号原文泄露** — `csvCell`（line 24-27）只转义了引号/逗号/换行，未对 Excel 会识别为公式前缀的字符（`=`、`+`、`-`、`@`）做防护（OWASP CSV Injection）；同时 `maskPhone`（line 15-18）对长度非 11 位的手机号直接原样返回、不打码。两者叠加：一旦手机号数据不是标准 11 位（脏数据/接口异常），会原文（未脱敏的 PII）且未转义地写入 CSV，运营在 Excel 打开时既泄露完整手机号，也存在被当公式执行的风险。修法：`csvCell` 对以 `=/+/-/@` 开头的单元格加前缀 `'` 或包一层文本转义；`maskPhone` 对非 11 位号码不应原样返回，至少做保守打码而非直接明文导出（这条降级行为 SPEC 未定义，落地时按此推荐处理，非纯编码 bug，见需求缺口部分）。

### P1

4. **[编码失误] 金额只保留 1 位小数** — `formatAmount`（line 20-22）用 `toFixed(1)`，SPEC 第 3 条明确要求「保留两位小数」，例如 12.5 元应显示 `12.50` 而非 `12.5`。改成 `toFixed(2)` 即可。

5. **[需求缺口] 时区边界未定义** — `exportOrders.ts:53-54` 用 `new Date(startYmd/endYmd)` 隐式按 UTC 解析日期边界，`order.createdAt` 也直接按 Date 原生比较。SPEC 未说明业务时区。如果订单创建时间实际以本地时区（如 UTC+8）记录，边界会偏移最多 8 小时，导致"当天"订单跨天误判。需要产品/需求方确认：日期筛选的"当天"是否统一按某个业务时区（建议 UTC+8）计算，而不是隐式 UTC。当前实现按推荐方案（UTC+8）需改动 `inRange`/边界计算逻辑。

### P2（仅标题）

6. 无效日期输入未校验（`startYmd > endYmd` 或格式错误时静默产出 Invalid Date 文件名/空结果，无报错）
7. `status` 列直接输出英文枚举值（pending/paid/shipped/cancelled），未做中文本地化——需求缺口，需确认运营端展示文案
8. `createdAt` 直接用 `toISOString()` 导出 UTC 格式（带 `Z` 后缀），未转成运营习惯的本地可读时间格式——需求缺口

### 总体评估
两个 P0 编码失误（未过滤已取消订单、结束日当天数据整体丢失）会导致该功能在任何一次使用中都产出与需求不符的数据，必须先修复再上线；CSV 注入/异常手机号泄露属于安全加固项，建议一并处理，其余为格式/边界类问题。

# 订单导出功能 Review

## P0（安全漏洞或静默错误数据）

1. **[编码失误] 已取消订单未被过滤，泄漏进导出结果**
   `buildCsv` 里过滤条件是 `.filter((o) => o.status !== "pending")`，只排除了 `pending`，`cancelled` 状态的订单会原样进入 CSV。SPEC 第 2 条明确写"只导出已支付和已发货的订单，已取消的不导出"，需求已经写死了白名单（paid/shipped），这里应改成 `["paid","shipped"].includes(o.status)`，而不是黑名单排除 pending。

2. **[编码失误] 金额只保留一位小数，与需求不符**
   `formatAmount` 用的是 `(cents/100).toFixed(1)`，SPEC 第 3 条明确要求"保留两位小数"。例如 `1230` 分应输出 `12.30`，当前会输出 `12.3`，运营在 Excel 里核对金额时会看到错误精度。改成 `.toFixed(2)` 即可。

## P1（边界/时区类正确性问题）

3. **[编码失误] 结束日期当天的订单被完全排除**
   `inRange` 用 `createdAt < end`，且 `end = new Date(endYmd)` 是 endYmd 当天 00:00。这意味着结束日期这一整天的订单全部被排除在外（不是"含当天"而是"完全不含"）。SPEC 第 1 条明确"两端都含当天"，需要把上界改成 endYmd 的次日 00:00（即 `end` 往后推一天），条件改回 `< nextDayOfEnd` 或用 `<=` 配合当天 23:59:59.999。

4. **[需求缺口] "当天"按哪个时区算，SPEC 未说明**
   `new Date(startYmd)` / `new Date(endYmd)` 按 ISO 8601 规则解析成 **UTC** 零点，但运营选的"开始日期/结束日期"大概率是以业务时区（通常是北京时间 UTC+8）理解的自然日。如果 `createdAt` 是真实时间戳，边界附近（尤其午夜前后 8 小时）的订单会被错误地划入/划出。需要回需求方确认：系统的"一天"是以 UTC 天还是北京时间天为准？当前实现按 UTC 处理，与业务时区预期大概率不符。

5. **[需求缺口] 手机号非 11 位时直接原样输出，绕过打码**
   `maskPhone` 里 `if (phone.length !== 11) return phone;`——一旦手机号格式不是标准 11 位（历史脏数据、带分隔符、国际号码等），打码逻辑整体失效，未脱敏的手机号会直接写入可能被多人打开核对的 CSV 文件，存在 PII 泄漏风险。SPEC 没有覆盖这种异常格式该怎么处理，需要产品/需求方给出兜底策略（例如"无法识别标准格式时仍按前 3 后 4 打码，不足则用能打码的部分处理"），当前"不打码直接输出"不应作为默认行为。

## P2（功能缺失/技术债，仅标题）

- CSV/Excel 公式注入防护缺失（`csvCell` 未处理以 `=`/`+`/`-`/`@` 开头的单元格）
- "创建时间"列直接输出 `toISOString()`（UTC、带 T/Z），格式是否为运营期望的展示格式未与需求方确认
- 订单号若为纯数字字符串，Excel 打开 CSV 时可能被误判为数字（丢前导零/转科学计数法），需确认 id 的实际格式
- "状态"列输出原始英文枚举值（paid/shipped 等），是否需要转成中文展示未在需求中说明
- `startYmd`/`endYmd` 传入非法日期字符串时会静默生成空 CSV，无任何报错提示

## 总体评估

两个 P0 属于对已写明的需求点的直接实现错误（取消单未过滤、金额精度错误），必须修复后才能用；P1 里的日期边界和时区问题需要回需求方确认业务时区约定后再定修复方案，手机号兜底策略也需要产品拍板。

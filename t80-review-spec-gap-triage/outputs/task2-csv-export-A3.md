## P0（安全漏洞或静默错误数据）

1. **已取消订单未被排除** — `src/exportOrders.ts:35`：过滤条件是 `status !== "pending"`，只排除了 pending，`paid`/`shipped`/`cancelled` 全部放行。SPEC 第2条明确要求"已取消的不导出"，现状是已取消订单会静默混入导出文件。
2. **金额精度错误** — `src/exportOrders.ts:21`：`formatAmount` 用 `toFixed(1)`，只保留一位小数；SPEC 第3条要求两位小数。运营拿这份 CSV 去 Excel 核对金额，"12.30 元"被静默导出成 "12.3"，属于财务数据静默出错。

## P1（边界/时区类正确性问题）

3. **结束日期几乎整天丢失** — `exportOrders.ts:29-30` 的 `inRange` 用 `createdAt < end`，而 `end = new Date(endYmd)`（`exportOrders.ts:54`）是结束日当天 00:00:00.000。凌晨 0 点之后创建的订单一律 `>= end`，被排除在外，等于结束日整天基本被丢弃，直接违反 SPEC "两端都含当天"。应改为次日零点或 `endYmd 23:59:59.999`。
4. **日期解析时区与业务时区不一致** — `new Date(startYmd)`/`new Date(endYmd)`（`exportOrders.ts:53-54`）把 `YYYY-MM-DD` 按 UTC 零点解析，但国内运营后台的"当天"边界通常是 UTC+8。两者相差 8 小时，会让区间首尾附近的订单被错误纳入或排除。
5. **手机号非 11 位时脱敏失效** — `maskPhone`（`exportOrders.ts:16`）在 `phone.length !== 11` 时原样返回，未打码。任何格式偏差（含国家码、空格、连字符等脏数据）都会导致完整手机号明文出现在导出文件里，违反 SPEC 第4条的强制打码要求。

## P2（功能缺失/技术债，仅标题）
6. CSV 单元格未防御 Excel 公式注入（`=`/`+`/`-`/`@` 开头值）
7. `dir` 参数拼接文件路径，未做路径穿越校验
8. 无效日期字符串 / start > end 无输入校验
9. `csvCell` 转义正则 `/[",\n]/` 未覆盖单独出现的 `\r`

**总体评估**：三条核心业务规则（状态过滤、金额精度、日期区间闭合）都与 SPEC 不符且都是静默数据错误，不能直接上线，需先修复 P0/P1 并补充对应边界测试（结束日当天订单、取消订单、非标准手机号）再复审。

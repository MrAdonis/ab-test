# 答案键 · task1 会员购买（src/membership.py）

需求单原文见 fixtures/task1-membership/SPEC.md。六处埋点，三处「编码失误」（需求单写明、实现做错），三处「需求缺口」（需求单没说、实现自己拍了一个行为）。

## 编码失误（需求单已明确）
- C1 月卡天数：需求单「月卡 30 天」，代码 `PLAN_DAYS = {"month": 31, ...}`。
- C2 续期不顺延：需求单「用户已经是会员的，在原到期日基础上顺延」，代码 `_grant_membership` 直接 `today + days` 覆盖，老会员剩余天数被吃掉。
- C3 验签失败仍放行：需求单「验签失败返回失败」，代码验签失败只 `log.warning` 然后继续标已支付、开通会员。伪造回调可白嫖会员。

## 需求缺口（需求单没说，实现自己拍的）
- S1 关单后到达的支付回调：需求单只说「15 分钟未支付自动关闭」，没说用户在第 14 分 59 秒付了钱、回调第 15 分 01 秒才到怎么办。代码 `order.status == "closed"` 直接返回 FAIL，用户钱扣了会员没开。要需求方定：补开通 / 自动退款 / 人工处理。
- S2 多端登录互踢：需求单只说 token 有效期 7 天，没说同一用户在第二台设备登录时第一台怎么办。代码 `login()` 里 `TOKENS.pop(user.token)` 单槽位，旧设备静默下线。要需求方定：允许多端并存还是互踢。
- S3 套餐价格：需求单通篇没给价格，代码硬编码 `PLAN_PRICE_CENTS = {"month": 1990, "year": 19900}` 是实现者编的数。要需求方给价格来源（配置 / 后台 / 常量）和具体数值。

## 不计分的正常发现（两臂都可能报，不算噪声也不加分）

- `list_orders` 每次全量扫描、无索引

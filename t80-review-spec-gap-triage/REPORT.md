# t80 · Code review 发现先分「需求缺口」还是「编码失误」

**结论：KEEP**，入 `~/.claude/agents/code-reviewer.md`；held-in 通过，held-out 结构性豁免（见文末）。第二轮追加的「搜寻步」变体 H 无增益且引入误报，不入配。

日期：2026-09-10
候选来源：X 帖 `x.com/ErwinWu000/status/2094991204375240733`（Erwin 的 AI coding 三步框架，引卡颂观点：AI review 出的 bug 大多是「需求没对齐、AI 脑补」，不是编码失误）。原帖是经验断言，本次把它做成 reviewer 侧的可测条款。

## 候选条款（B 臂）

见 `prompts/candidate-clause.txt`。核心四条：每条发现先按「需求单原文有没有覆盖该场景」判来源；编码失误给具体修法；需求缺口写成要需求方回答的问题 + 当前实际行为 + 推荐答案，交回需求方定；每条带 `[编码失误]` / `[需求缺口]` 标签，需求缺口不因为「不是 bug」就省略。

## 设计

| | |
|---|---|
| A 臂 | `prompts/rules-A.txt`：现行 code-reviewer agent 规则（appsec 面对照 / 占位密钥按生产可达性 / P0-P2 定级 / ≤1500 token） |
| B 臂 | A + 候选条款 |
| H 臂（第二轮） | A + `prompts/hunt-clause.txt`（逐行看码前先对照需求单找硬编码常量 / 未定义分支 / 一句话带过处）+ 候选条款 |
| 生成 | sonnet，`run.sh`，每个 (task, 臂, 次) 独立沙箱；A/B 各 3 次，H 2 次 |
| 裁判 | opus，**单篇独立对账**（不做并排盲评，避开槽位效应，见 memory `feedback_ab_pairwise_slot_bias`），`judge/rubric-single.md` + 答案键 |
| 确定性前置 | `keyword-scan.py` 按埋点正则粗数发现数，与裁判发现列交叉核对 |

两个 fixture 各埋 3 条编码失误（C1-C3，需求单写明、实现写错）+ 3 条需求缺口（S1-S3，需求单没写、实现自己拍板）：

- **task1 微信登录+会员购买**（Python）：C1 月卡 31 天（spec 写 30）/ C2 续费覆盖不顺延 / C3 验签失败只 log 不 return；S1 已关闭订单收到支付成功回调（钱扣了、会员没开）/ S2 登录踢旧 token 单端在线 / S3 套餐价格硬编码而 spec 没给价
- **task2 订单 CSV 导出**（TS）：C1 过滤只排 pending 把 cancelled 漏进去 / C2 `toFixed(1)` / C3 结束日当天被排除；S1 无 BOM 中文表头 Excel 乱码 / S2 时区口径 / S3 状态列输出英文枚举

每个埋点按 发现 / 归因 / 处置 各 0-1 计分，单份满分 18；另计 误报数 和 需求缺口误判数（把 spec 已写明的当需求缺口开脱）。非埋点正常发现（占位密钥、公式注入、手机号非 11 位）不计分不计误报。

|---|---|---|---|---|---|---|---|
| A | 9 / 9 / 9 | 13 / 11 / 10 | **10.2** | 1.2 | 9/9 全满 | 0 | 0 |
| B | 9 / 12 / 15 | 16 / 11 / 15 | **13.0** | 4.0 | 9/9 全满 | 0 | 0 |
| H | 9 / 13 | 15 / 12 | 12.3 | 3.3 | 9/9 全满 | 1 | 0 |

- 差异**全部在 S 类**（需求缺口）：A 六份合计 7/54，B 六份合计 24/54。C 类两臂全部 9/9，条款没有稀释对编码失误的处理
- 按生成次配对，B 六对全部 ≥ A（四对严格大于，两对打平）
- **无代价观察到**：六份 B 里没有一条把 spec 已写明的 C 类推给需求方（需求缺口误判 0），误报 0
- 方差真实存在：B 在 task2 从 11 到 16，与效应量同量级。三次生成后方向稳定，但单次 B 可以跑出与 A 一样的分（task1 B1 = 9）

## B 赢在哪

条款主要作用在**归因 + 处置**，其次才是发现。拆开看六份 B 的 18 个 S 埋点：发现 10、归因 8、处置 7；六份 A：发现 6、归因 1、处置 0。A 臂即使看到了（task2 A1 同时发现 BOM / 时区 / 状态列三条），也全部写成「违背 spec」要实现者自行改，没有一条交回需求方。

典型对照（task2 S2 时区）：

- A1：「若订单以本地时区为准，边界会整体偏移」——判为 bug，修法是「改成东八区」，实际 spec 没说是哪个时区
- B1：「SPEC 未说明时区口径…需产品/需求方确认预期时区，当前实现按 UTC 处理，建议按运营所在地北京时间」

**条款不管搜寻**：task1 S3（价格硬编码 spec 没给）六份 B 里 0 次发现，S1（已关闭订单收到回调）2 次。这是第二轮做 H 臂的动因。

## H 臂为什么不入配

H 在候选条款前加了一个「逐行看码前先对照需求单找三类未定义行为」的搜寻步。结果 S 类均分 3.3 < B 4.0，task1 H1 还把「超时订单未被 cron 关闭却标已支付」这条反方向的场景当真问题报了（唯一一条误报）。两次生成样本小，但方向上搜寻清单没让模型找到它本来找不到的 S3，反而给了它一个按清单造发现的入口。**方向级结论**：给 reviewer 加「按清单搜某类问题」的前置步骤，默认先疑它会诱发凑数，不是补搜寻盲区的解法。

## 已知噪声

- 裁判对「答案键外的额外发现」一律按「代码真实行为则不计误报」处理，两臂同标准
- task1 三份 A 在 S 类全部 0 分，task2 A 反而 4/2/1——需求缺口的「可发现性」与领域有关（CSV 的 BOM/时区是通用坑，会员系统的价格来源不是），fixture 只有两个领域

## held-in 回归

HELDOUT §H2（dirstat.py）由 sonnet 中立生成（`heldin/gen.sh gen`，不带评测线索），双臂各审一遍，opus 盲评（甲=A 乙=B，`heldin/mapping.txt`）。本机没装 pytest，artifact 测试未在本地跑，B 臂在沙箱里自己跑了 11 passed。

| | 覆盖面 | 真实性 | 归因与处置 | 可用性 | 合计 |
|---|---|---|---|---|---|
| A | 6 | 9 | 4 | 5 | **24** |
| B | 8 | 8 | 9 | 9 | **34** |

**B 更好，靶向维度（归因与处置）+5，held-in 通过。** 两臂都抓到了不可访问文件被静默跳过、`success: true` 却漏计这个 P0。差异在处置：A 把它和符号链接语义一并断言为缺陷「修复后再合入」，不给修法也不给需求方选项；B 标需求缺口，给当前行为 + 三个选项 + 推荐（结果里加 `skipped` 字段），并额外抓到「递归语义本身是实现拍板的」。

**真实代价（裁判扣了 B 真实性 1 分）**：B 把「`--json` 非默认」也标成需求缺口，但 spec 原文「支持 `--json`」已经把它定成 flag，这是拿内部 DoD 去质疑需求方已决定的事。条款让模型更愿意把东西交回需求方，边界上会多问一两条价值低的。A 独有的符号链接跟随语义不一致那条 B 漏了。

## held-out 结构性豁免

HELDOUT 的 H1（推文）/ H3（CF Pages 排查）不跑：条款写在 `~/.claude/agents/code-reviewer.md`，只在派 code-reviewer 子代理时加载，写作和诊断任务全程不可达。若日后上移到 `rules/coding.md` 或 cross-review skill（常驻或多入口），此豁免失效，必须补跑。

## 入配措辞收窄

条款原文照入，另加一句适用前提：有需求单 / spec / task_plan 验收条件可对照时才做此分类；纯 diff review 没有需求文本时按常规定级。fixture 全部带 SPEC.md，无需求文本场景未测。
